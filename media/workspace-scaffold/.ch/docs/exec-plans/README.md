# 执行计划

本目录仅记录 `feature`、`bugfix`、`refactor`、`perf` 类型的非平凡、多阶段、跨模块或高风险任务。这里是计划命名、分类、拆分、状态与归档规则的单一事实来源；根级 `AGENTS.md` 仅提供导航。

`test`、`chore`、`doc`（含 `docs`）类型任务不在本目录创建或归档计划，也不得改名为允许类型来绕过排除规则。独立的测试、维护或文档任务使用任务列表、测试记录或对应事实来源文档；相关测试、维护和文档工作属于某份允许类型计划的交付范围时，在该计划中记录范围、验收与验证结果，不另建计划。排除计划文件不免除测试、验证和文档同步要求。

## 文件与类型

真实计划文件名严格为 `YYYY-MM-DD-<type>-<kebab-case-slug>.md`，日期后紧接且只出现一个 type。允许类型仅为 `feature`、`bugfix`、`refactor`、`perf`，不得缩写为 `feat` 或 `fix`。

| Type | 含义 |
| --- | --- |
| `feature` | 新功能开发 |
| `bugfix` | 修复已发布版本中的 bug |
| `refactor` | 行为保持的重构 |
| `perf` | 性能优化 |

一个任务包含多个允许的实质工作类型时，必须按允许类型分别建计划。每份计划都要有自己的目标、范围、验收标准、验证计划和真实状态；“关联计划”填写具体相对路径并记录共同背景与依赖。禁止只选主类型、混合多个允许 type，或复制整篇混合正文假装拆分；实际跨类型工作不得隐藏在附带事项中。`test`、`chore`、`doc`（含 `docs`）不参与计划拆分。

跨类型示例：新功能与独立性能优化分别记录为 `active/2026-11-11-feature-workspace-search.md` 和 `active/2026-11-11-perf-workspace-search-index.md`，两份计划用具体相对路径互链并说明依赖；各自维护目标、范围、验收、验证和状态。新功能所需的回归测试开发和文档同步直接记入功能计划，不创建 `test` 或 `doc` / `docs` 计划。

## 目录与状态

- `active/`：正在推进的计划。
- `completed/YYYY-MM/`：按计划日期月份归档的已完成计划，不要平铺在 `completed/` 根目录。
- `TEMPLATE.md`：新计划模板。
- `migrations/`：可选迁移审计资料，不替代计划正文或状态。

拆分不伪造完成，也不改变既有阻塞状态。只有头部状态为 `completed` 才能归档；迁移计划后更新并验证仓库内具体引用。枚举历史计划时递归扫描 `completed/**/*.md`，以完整相对路径标识。

每份计划至少记录背景、目标、范围和非目标、验收、影响面、风险、验证计划、测试结果、相关文档同步、进展与下一步。收尾时明确已验证及未验证内容。
