# 项目架构说明

> 这是目标项目的架构骨架模板。接入到真实项目后，请用项目真实目录、真实模块名、真实边界替换示例内容。
> 这份文档只回答架构问题：代码应该放哪里、依赖可以怎么走、扩展时不能破坏什么。

## 1. 文档目标

本文件至少回答下面三个问题：

1. **项目目标结构是什么**：目录如何分层，各目录放什么，不放什么。
2. **分层边界是什么**：模块之间允许哪些依赖，禁止哪些跨层耦合。
3. **扩展规则是什么**：新增功能、服务、页面、脚本、模块时，应该落到哪里。

## 2. 目标结构

下面是一个可裁剪的推荐骨架，请按项目实际情况保留或删减：

```text
.
├── README.md
├── AGENTS.md
├── CLAUDE.md
├── ARCHITECTURE.md
├── .agents/
│   └── skills/
├── .ch/
│   └── docs/
├── apps/ 或 src/
│   ├── frontend/        # 前端应用 / 页面层 / 交互层
│   ├── backend/         # 后端应用 / 接口层 / 作业入口
│   └── jobs/            # 定时任务、异步任务、批处理入口
├── packages/ 或 libs/
│   ├── domain/          # 领域模型、核心规则、用例编排
│   ├── shared/          # 跨模块复用工具、类型、常量
│   └── integrations/    # 第三方系统适配、SDK 包装、网关
├── tests/
├── scripts/
└── infra/
```

如果你的项目不是 monorepo，也可以把上面的边界映射到单仓目录，例如：

- `apps/frontend/` 映射为 `src/pages/`、`src/app/` 或 `web/`
- `apps/backend/` 映射为 `src/server/`、`api/` 或 `service/`
- `packages/domain/` 映射为 `src/domain/`、`core/` 或 `modules/`

关键不是目录名字完全一致，而是**边界一致**。

## 3. 分层边界

### 3.1 推荐依赖方向

建议保持下面的单向依赖：

```text
交互层 / 接口层
        ↓
应用编排层 / 用例层
        ↓
领域层 / 核心规则层
        ↓
基础设施适配层
```

### 3.2 各层职责

#### 交互层 / 接口层

- 负责 HTTP、RPC、页面、命令行、消息订阅等入口。
- 负责参数解析、鉴权、协议转换、响应组装。
- 不承载核心业务规则。

#### 应用编排层 / 用例层

- 负责把一个完整业务动作编排出来。
- 负责事务边界、调用顺序、权限校验串联、日志上下文。
- 可以调用多个领域服务，但不应沉淀底层协议细节。

#### 领域层 / 核心规则层

- 放稳定业务规则、领域模型、状态变迁、核心校验。
- 不依赖 UI、HTTP 框架、数据库 SDK 细节。
- 允许被多个入口复用。

#### 基础设施适配层

- 负责数据库、缓存、消息队列、外部 API、文件系统等具体接入。
- 只实现适配，不反向决定领域规则。
- 外部系统变化应优先收敛在这一层。

### 3.3 明确禁止

- 页面层直接拼接数据库访问逻辑。
- 控制器 / handler 直接复制整段业务规则。
- 第三方 SDK 调用散落在多个业务目录，缺少统一适配点。
- 为了“快”把跨模块公共逻辑复制到多个地方。
- 让基础设施细节反向渗透到领域层。

## 4. 模块扩展规则

### 4.1 新增业务功能

新增功能时，按下面顺序判断落点：

1. 是不是已有模块能力的扩展？优先在原模块内演进。
2. 是否形成独立领域概念？若是，再拆新模块。
3. 是否只是入口不同、规则相同？优先复用领域层，不重复实现。

### 4.2 新增共享能力

只有同时满足下面条件，才进入 `shared` / `common`：

- 被至少两个模块复用。
- 语义稳定，不依赖单一业务场景。
- 不会因为放到共享层而反向制造更大耦合。

否则宁可先放在当前业务模块内，等复用真实出现后再上提。

### 4.3 新增第三方集成

- 每个外部系统应有明确适配目录或模块。
- SDK 包装、重试、限流、熔断、字段映射尽量集中。
- 不要让业务代码直接到处感知第三方接口细节。

### 4.4 新增脚本与工具

- 一次性排障脚本不要长期混在正式 `scripts/` 中。
- 可复用脚本应写明输入、输出、运行前提和风险。
- 涉及生产数据的工具应与相应业务模块或基础设施目录保持清晰归属关系。

## 5. 演进规则

### 5.1 允许的演进

- 在不破坏分层边界的前提下新增模块。
- 在保持公开契约稳定的前提下重构内部实现。
- 将重复逻辑收敛到更靠近真实归属的位置。
- 让外部系统差异更多地收敛在适配层，而不是扩散到业务层。

### 5.2 架构级变更

以下变化属于架构级变更，应先明确设计决策，再实施：

- 跨层依赖方向调整。
- 核心领域模型重构。
- 公共库大规模上提或下沉。
- 基础设施切换，例如数据库、中间件、核心框架替换。
- 会影响多个团队协作方式的目录重组。

## 6. 架构文档维护要求

出现下面情况时，必须更新本文件：

- 新增一级业务目录或核心模块。
- 调整分层职责或依赖边界。
- 新增明确的扩展约定。
- 把某类能力从“局部实现”提升为“共享规范”。

保持这份文档**短、准、可执行**。它应该帮助代理迅速做对目录决策，而不是变成过时口号集合。
