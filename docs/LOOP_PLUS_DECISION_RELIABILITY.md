# Loop+ 决策可靠性长期实施方案

## 目的与边界

目标是降低 Loop+ 主模型决策反复遭拒的概率及恢复成本，同时让每次拒绝能区分“输出不可解析”“决策数据/证据关联不合法”“当前宿主状态不允许该动作”。不把协议提示修复等同业务验收，不通过放宽校验、自动猜测验收结论或重排任务掩盖问题。

宿主持有调度状态及事件身份；模型只根据宿主给出的当前视图提出动作。验收冻结顺序、真实验收证据、开放验收批次门禁、失败返工和最终完成门禁均须保留。各 CLI 原生会话、结构化输出和工具调用能力继续按各自适配契约处理；公共 Loop+ 层不可假定 CLI 间能力等价。

本文区分当前工作树中已核对的行为与后续方案。`1.10.5` 是未提交、未发布的候选；源码核对及定向测试不是最终验收。验证边界见[在途计划](../.ch/docs/exec-plans/active/2026-11-25-bugfix-loop-plus-decision-json-diagnostics.md)。

## 源码核实的现状

- 解析入口为 `src/loopPlusDecision.ts` 的 `parseLoopPlusDecisionWithFeedback`：从代码块或解释文字中提取候选对象，再由 `parseLoopPlusJsonObject` 先尝试标准 JSON，失败后兼容 JSONC 注释和有效值后的尾逗号（参见 `src/shared/jsonObject.ts` 和 `.ch/docs/design-docs/loop-plus-scheduling.md`）。保留这些无损兼容，不猜测、补写或改写业务字段。解析后按 `status` 归一化；拒绝类别为 `format` 或 `validation`。格式诊断可带受控错误码及候选对象内行列，不包含原始回复。
- `accept.subtasks` 和 `dispatch.subtasks` 的已定位字段错误已有受控原因码、字段及适用的数组索引；不能从历史泛化文案反推具体坏字段。已有的任务归属校验是另一条路径：它检查未关联、指向不存在任务或重复关联，不得为补齐关系伪造失败结论或继承无关修复会话。
- 主提示在 `src/extensionHost/loopPlusPromptBuilders.ts` 构造，纳入当前验收/报告事件、任务视图、依赖、修复要求、可用额度及工作模式；`src/loopPlusDecisionContract.ts` 按宿主状态投影示例，不等于启用了各 CLI 的原生 schema。
- 宿主将已映射的状态拒绝归为 `state`，与解析器的 `format`、`validation` 区分。`src/loopPlusProtocolRepair.ts` 将受控修正提示附在新请求上；`src/extensionHost/loopPlusOrchestration.ts` 管理连续拒绝预算和暂停。计数、停止边界及实际日志字段见[调度设计](../.ch/docs/design-docs/loop-plus-scheduling.md#协议失败后的自动续跑)。
- 普通派发：`src/extensionHost/loopPlusDecisionStrategies.ts` 的 `applyDispatchDecision` 在 `hasCurrentReview` 时拒绝普通 `dispatch`；通常应以 `accept` 按冻结顺序确认整批，并在同一决策中附带适合的后续任务。
- 一次性验收前窗口：宿主可在首次领取符合条件的新批次时为当前 step 明确设置 `allowDispatchBeforeReview`。`loopPlusOrchestration.ts` 的 `applyDecision` 此时将 `dispatch` 交给 `applyDispatchBeforeReview`，而不是普通派发策略。协议形状为 `dispatch` 加有效的 `nextStepPlan`，不带 `reviewEventId`、`reviewEventIds`、`reviews` 或 `controls`；`reportEventIds` 必须按当前 step 冻结的报告顺序原样确认，无报告时可省略或用空数组。这是输出契约：解析器会拒绝派发携带的验收 ID，但不会因多余的 `reviews` 单独拒绝；宿主拒绝的是归一化后实际存在的控制操作。
- 窗口内也须符合单次派发上限、可用并发槽和轮次额度，且整份提案经预检均能立即启动。任务须使用新逻辑 ID，不续接已有子任务、不依赖待确认结果，与待验收交付无冲突；预检不通过不得部分派发或消费报告。成功时确认所给报告、保存计划，原冻结验收批次及顺序留给下一决策确认，不重开窗口。`src/loopPlusScheduler.ts` 仍持有实际队列与完成门禁；窗口既不确认验收，也不放宽完成条件。
- 主通信脱敏记录中，2026-11-25 06:24:04 UTC 的一次拒绝是 `accept.subtasks` 的任务 ID 与 `reviews[].subtaskIds` / `independentSubtaskIds` 的归属不匹配，关联指向 `fixture-unknown-task`（合成标识，表示不存在于本决策 `subtasks` 的任务）。这是验收关联校验失败，不是任务项自身无效或 JSON 语法损坏。
- 2026-11-25 10:23:01 UTC 的另一次拒绝是开放验收批次下误发普通 `dispatch`，属于宿主状态拒绝，不是 JSON 或字段解析失败。两条记录只证明这些暂停实例，不代表全部拒绝的主因。
- 用户在 2026-11-26 表示反复出现 JSON 格式问题，并认为问题从 1.9.x 开始。当前可核资料不能确认历史首次引入版本，也不能确认两次已记录暂停由格式错误触发；1.9.x 起点标为未知，需版本历史/对应原始日志补证后再定因。

## 拒绝分类与处理路径

| 类别 | 证据 | 处理路径 |
| --- | --- | --- |
| 格式损坏（`format`） | 无对象、交给解析器的内容为空、截断对象，或经过候选提取和 JSONC 兼容后仍无可解析对象 | 保留候选提取、JSONC 注释和有效值后的尾逗号；只提供受控错误码及适用的对象内位置，不猜测业务字段。空输入本身不证明模型实际给了空回复。 |
| 字段/验收关联失败（`validation`） | 对象可解析，但 `status`、数组项、任务字段、依赖字段形状、决策内事件顺序或任务归属等约束失败 | 用稳定原因码定位并保留已有证据；区分 `accept.subtasks` 项自身无效与验收归属失败。不重跑业务。 |
| 宿主状态拒绝（`state`） | 对象通过解析校验，但与宿主冻结 ID、报告顺序或状态门禁不符；如窗口关闭时的普通 `dispatch`，或窗口内不满足立即启动条件 | 给出状态原因码及当前可用形状。窗口关闭或不具备合规工作时，按原顺序验收，不自动改写决策、确认验收或重排队列；合规的一次性窗口派发不是拒绝。 |

## 分阶段推荐方案

### 阶段 0：建立脱敏基线与原因码

盘点解析、各状态 normalizer、prompt builder、协议续跑、策略拒绝和暂停摘要；将拒绝整理为稳定、版本化的原因码，例如 `format.invalid_json`、`validation.accept.subtasks.invalid_item`、`validation.accept.subtask_linkage.mismatch`、`state.review_batch_open.dispatch_forbidden`。对现有拒绝补齐分类，不改变放行条件。统计不使用任务内容、提示正文、CLI transcript、路径、密钥或原始模型输出。

合成夹具：代码块或解释文字中的对象、JSONC 注释、有效值后尾逗号均可解析；空输出、无对象、截断字符串/数组、缺失值或空容器中孤立逗号归为 `format`。可解析但 `status` 错误、缺字段、任务项无效、验收归属重复/未知/遗漏，以及 `reviews` 顺序与决策声明不符，归为 `validation`。报告顺序与宿主冻结顺序不符或窗口条件不满足归为宿主状态拒绝；同一合法 `dispatch` 在窗口打开且可立即启动时通过，窗口关闭且验收仍开放时拒绝（见阶段 2）。

通过条件：兼容用例与对应标准 JSON 归一化结果一致；拒绝用例稳定落到预期类别与原因码；不把窗口内的合规派发计作失败，既有策略边界不变。脱敏观测只保留分类、原因码、状态（含窗口开关）、尝试序号、模型/CLI 能力档位（非凭据）、是否续跑及最终结果。

回滚：关闭新原因码观测/映射，恢复旧文案；不涉及持久调度格式迁移。

#### 2026-11-26 UTC 阻塞基线

观察窗仍是 `2026-11-26T00:00:00.000Z`（含）至 `2026-11-27T00:00:00.000Z`（不含）。归属仍以宿主事件时间为准：协议暂停用任务记录中的宿主暂停标记，标记内的纪元毫秒须与标记下的时间字段一致；准入用性能日志的 `attempt-admission` 时间；测试进程等待用子任务报告中的观察时钟换算到 UTC。用户转述、提示和文档例子不另计。当日主日志没有 `loop-plus-protocol-miss` 或 `loop-plus-protocol-recovery`。代号 P1–P5、S1–S8 沿用此前对照，不在本文展开任务标识。

工作区样本只保留任务库中 `workspaceKey` 与存储目录前缀都和本任务记录相同的父任务。已核对的 P1–P5 里，只有 P4 满足。该前缀下的其余父任务记录在观察窗内没有宿主暂停标记。因此本工作区可证实的协议暂停是 P4 的 7 次，不是跨工作区的 25 次。25 次暂停、5 个父任务，以及准入 9/349，只作为跨工作区背景；它们的分母含有其他 `workspaceKey`，不能当作本工作区的比例。

**本工作区的协议暂停。** 7 次都写明首次拒绝之后已经自动继续：5 次为 1 次，2 次为 3 次，然后实际暂停。暂停打断的是主决策循环。恢复分成三种，分母都是这 7 次：

- 已观察到的新派发：该次暂停之后、下一次同父任务协议暂停之前，至少一份新子任务沟通文件的创建时间落在开区间。
- 窗末可证实仍暂停：开区间一直延伸到窗末仍没有这样的文件，且暂停之后没有该父任务的 `loop-group-chat-continue-received`。
- 终态未知：下一次协议暂停已经出现，但开区间内没有新文件。这不能区分只做了验收，还是续跑决策再次被拒。

| 类别 | 次数 | 已观察到的新派发 | 窗末仍暂停 | 终态未知 |
| --- | ---: | ---: | ---: | ---: |
| `format.EmptyResponse` | 4 | 3 | 0 | 1 |
| 修复关联被拒，记录没有稳定原因码 | 1 | 0 | 0 | 1 |
| `state.review_batch_open.wait_forbidden` | 1 | 1 | 0 | 0 |
| `validation.invalid_decision` | 1 | 0 | 1 | 0 |
| 合计 | 7 | 4 | 1 | 2 |

4 次空回复都带有 `EmptyResponse` 代码。其中 3 次的开区间内新文件数分别是 1、4 和 13。`03:04:46.023Z` 到下一次暂停之间没有新文件，终态未知。`03:20:59.496Z` 的模板写明失败项必须关联修复子任务，没有稳定原因码，到 `03:22:29.530Z` 之间也没有新文件，终态未知。`08:12:05.002Z` 的 `wait_forbidden` 自动续跑 3 次，开区间内有 4 份新文件。空回复占本工作区协议暂停的 4/7。

核对例：P4 在 `2026-11-26T10:37:46.071Z` 的宿主暂停，原因码是 `validation.invalid_decision`，自动续跑 3 次。按上面的工作区筛选，这次属于本工作区。从该时刻到窗末，P4 没有新的子任务沟通文件，也没有 `loop-group-chat-continue-received`。它因此计入上表该原因码的 1 次，并计入「窗末仍暂停」的 1 次。

**本工作区的执行准入。** 性能日志的 `attempt-admission` 行没有工作区或父任务字段。跨工作区背景是 349 次尝试中 9 次 `denied`，即 9/349；这个分母不能用于本工作区。本工作区可证实的下限是 1 次，而且属于时间邻近推断：`2026-11-26T05:34:06.564Z` 的 `denied` 之前 0.191 秒，P4 的 S3 沟通文件被创建，当时执行报告仍是空模板，附近没有第二份空模板。S3 在 `2026-11-26T05:45:21.602Z` 有同一逻辑子任务的后续非空报告，这是已观察到的新报告，不是日志里的同标识回执。其余按时间邻近落到 P1–P3 的记录不属于本工作区。`01:53:56.724Z` 与 `03:39:10.008Z` 两次 `denied` 没有唯一空模板，工作区归属未知，不计入下限。本工作区的准入比例未知。

**本工作区的测试等待。** 可确认 1 次，父任务 P4，子任务 S8。报告观察时刻是 `2026-11-26 17:51:35`（Asia/Shanghai），即 `09:51:35Z`。全量测试驱动已运行 1 小时 2 分 31 秒，两个测试进程仍在等待事件。同一父任务主记录和群聊中的转述不另计。没有本工作区全部测试运行的分母，不写比例。

- 测试驱动退出：报告写明原运行没有被终止，最终统计和退出码都没有。窗内没有该驱动退出的后续记录。退出结果未知。
- 标签关闭：宿主日志在 `09:53:19.751Z` 与 `09:53:22.612Z` 对同一子任务记下两次关页错误，原因都是执行身份无法核验，第二次不再重试。这是已观察到的关闭失败，不能代替驱动退出。

**模拟优先级。** 本工作区有协议暂停的父任务只有 P4。`format.EmptyResponse` 是这 7 次里的 4 次，其中 3 次之后已经观察到新派发，同一种空回复仍再次出现。这是本工作区最应先模拟的故障。`validation.invalid_decision` 是唯一一次窗末仍可证实处于暂停，占 1/7，作为下一项。时间邻近推断的准入拒绝有后续非空报告。测试驱动是否退出仍未知，标签关闭失败单独保留，不与协议空回复合并计数。

本基线不改变放行条件。仍缺的是：本工作区主决策次数，因此没有工作区协议暂停率；两次终态未知的协议间隔是否只做了验收；两次未能定位的准入拒绝是否属于本工作区；S8 两个等待进程在报告之后是否退出。

### 阶段 1：共享决策契约及合成示例

从解析器的类型与校验规则生成或校验按 `initial`、`review`、`closeout` 等宿主状态区分的契约摘要与 JSON 示例。优先使用可由 TypeScript 类型/显式契约定义校验的单一来源，避免另建一份漂移的 JSON Schema。若现有 schema 工具无法表达跨字段约束，保留手写语义校验，契约检查器仅覆盖结构并明确边界。将提示 builder 的示例改为读取同一契约/fixtures；拒绝后给最小修正片段而不是完整重复所有文档。

合成夹具：每个 status 最小合法对象、各字段边界、事件列表顺序、accept 的任务关联集合一一覆盖、独立子任务、失败修复和取消原因；非法近邻样例必须被拒绝。

通过条件：所有提示示例在 parser 中通过；所有拒绝示例保持拒绝；生成的状态契约与解析器测试使用同一 fixtures；差异必须显式审核，不靠快照更新掩盖语义变化。脱敏指标按原因码统计首次通过率及校验拒绝分布，不采集正文。

回滚：恢复上一版提示模板/示例；parser 与调度门禁不回退、不放宽。

### 阶段 2：宿主按状态提供“当前可用决策形状”

让宿主从冻结 step 和 scheduler 快照只读派生本步形状，不以提示取代应用时预检。无开放批次时可展示常规派发等适用形状；批次开放时展示按原顺序逐项 `accept` 的形状。只有宿主显式开放一次性窗口时才额外展示 `dispatch + nextStepPlan`：按冻结顺序回执报告，省略验收 ID、`reviews` 和 `controls`，且仅派发全部可立即启动的无冲突独立新任务。窗口不是通用派发权限，也不替代 `accept` 或满足门禁后的 `completed`。

成对合成夹具（两侧均有开放批次；验收事件和报告均按宿主冻结顺序给出）：

| 通过 | 对照拒绝 | 核验 |
| --- | --- | --- |
| 窗口打开；有一空槽，额度足够；提交带计划及顺序正确报告回执的一个独立新任务 | 只关闭窗口，提交同一决策 | 打开时立即启动、保存计划、仅确认所给报告；原验收前缀不变，下一次仍须确认且窗口不重开。关闭时由普通策略拒绝。 |
| 窗口打开；计划与报告回执正确，不带确认验收字段或控制动作 | 分别省略 `nextStepPlan`、交换两个报告 ID、附加实际控制操作，或携带 `reviewEventId` / `reviewEventIds` | 前三项由窗口路径拒绝；验收 ID 由派发归一化拒绝。提示示例也必须省略 `reviews`，不把解析器忽略该字段当作许可。 |
| 窗口打开；提案数量在上限内且预检全部可立即启动 | 分别超出派发上限、可用槽位或轮次额度，复用旧 ID、要求续接、依赖待确认结果、与待验收交付冲突，或预检只能得到排队结果 | 数量超过解析上限在字段校验拒绝，其余按宿主预检门禁处理；不得仅启动合规子集、消费报告或改变原冻结批次。 |

通过条件：上述两方向与宿主分支一致；同样覆盖无批次、单项/多项冻结验收、仅回执报告、运行/排队、欠返工和最终收口。冻结事件与报告顺序原样传递；未确认事件/报告、未消费用户消息、运行或排队任务、欠返工仍阻止完成。脱敏观测只记录契约版本、状态类别、窗口开关和预检结果，不记录提示或事件 ID。

回滚：关掉新投影，回到现有提示构建；宿主校验与冻结队列完全保留。

### 阶段 3：按 CLI 适配能力使用结构化输出

逐个核对现有 CLI adapter 在适用平台上的原生输出格式/JSON schema 能力、版本条件、流式解析及错误语义，保留各自参数、会话、压缩、用量及输出传输差异。仅在适配器明确支持且可以按原契约传递 schema 时启用结构化输出；公共层不统一注入某 CLI 专属参数。无支持或能力未知的适配器沿用文本提示、候选提取、JSONC 注释和有效值后的尾逗号兼容，以及状态示例和阶段 4 的有界续跑。格式兼容不猜测业务字段；结构化输出也不代表跨字段合法或宿主允许。

合成夹具：模拟支持／不支持／能力未知的 adapter，确认原生参数只发给匹配 adapter。两条路径都复用阶段 2 成对用例：相同形状在窗口内合规时通过，窗口关闭或报告顺序、容量、独立性等条件不满足时拒绝；字段坏值和错关联也仍拒绝。文本路径另复用阶段 0 的候选提取、注释、有效值后尾逗号与实际格式损坏用例。

通过条件：每个 CLI 单独满足其 adapter 契约，无全局回退静默改变调用语义；结构化与兼容路径最终共享相同校验器和调度门禁。脱敏指标仅记 adapter 能力版本、结构化开关、类别/原因码及结果。

回滚：按 adapter 独立关闭结构化输出；所有模型回落至既有文本提示路径，不修改会话身份或 scheduler 状态。

### 阶段 4：带原因码的最小续跑和渐进启用

当前候选在原主任务会话内最多自动请求三次新决策。初始拒绝计为第 1 次失败，不占三个自动请求名额；三次续跑均拒绝时，第 4 次连续拒绝进入 `needs-review`，不再请求下一次，也不是完成或用户停止。暂停保留未确认验收、FIFO 报告、待处理消息和既有调度预留。自动续跑不提升 pending、不重置计数；宿主接受有效决策或准入用户显式继续（有无补充说明均可）后重置。手动请求本身不是自动续跑；其返回的决策再被拒绝才开始新链。停止、已确认取消、释放或完成后不得发起新的协议续跑。

新请求只在正常快照和当前可用形状上附加受控类别、原因码、适用字段/候选行列及修正提示，不回灌原始拒绝回复或自由文本理由。诊断日志不含 prompt、回复正文、凭据或本地路径；候选行列用于修正提示而非协议日志字段。续跑不自动 `accept`、`dispatch` 或 `complete`。

合成夹具：三类拒绝、预算内恢复、三次续跑均拒绝、手动继续后重新计数，以及停止或取消后不再请求。验证已有事件不重复确认、任务不重复启动、已有验证证据不重跑；旧暂停原因码未知时用通用安全提示。

通过条件：新旧路径影子比较无门禁差异后小流量启用；首次拒绝到成功恢复率提升、同一原因重复拒绝率下降，且状态不变量测试全通过；不能以“暂停率下降”作为唯一成功指标。日志可用脱敏关联 ID、粗粒度时间/尝试计数、原因码、拒绝类别、adapter 能力、恢复/暂停结果；禁记完整 prompt、响应、项目/用户标识及秘密。设定留存期限并限制访问。

回滚方案待审定：按适配器独立回退结构化输出；若需回退续跑模板或预算，保留安全原因码观测及原 scheduler 持久状态，不清理队列、不伪造验收。此处不表示已有功能旗标。

## 顺序、验收与未决问题

阶段 0–2 和阶段 4 的候选交付及验证缺口见在途计划；阶段 3 仍需按 CLI 与平台逐一核实，阶段 4 灰度与观测指标尚未验证。每阶段以 parser、策略、调度器、提示契约和适配器的相关测试为最小回归，再扩大验证。功能清单和 Ontology 随调度契约同步，不替代运行证据。

需主审确认：原因码是否作为独立持久字段、prompt 契约 schema 的具体承载形式、各 CLI 当前支持矩阵及观测留存策略。历史首次发生于 1.9.x 的说法仍未证实；需取对应版本源码/提交和脱敏原始故障记录做时间线比对后才能归因。
