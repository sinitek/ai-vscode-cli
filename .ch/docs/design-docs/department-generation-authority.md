# Department Generation Authority

## Purpose

`DepartmentGenerationAuthority` is a cross-process coordination primitive for one exact leader generation. Its identity is the tuple `rootTaskId`, workspace, leader task, module, generation, and original `producerId`. A protected per-generation directory and authenticated local IPC endpoint are created by the original production lifecycle before `DepartmentLeaderExecutionLedger.open` and before the first scheduler pump.

The independent authority process serializes snapshot updates. Requests use protocol version 2 and include request ID, token, exact scope, and expected claim. Readiness is an asynchronous IPC barrier; the Extension Host does not synchronously poll or block its event loop. The server rejects stale claims, malformed frames, excessive frames/connections/tickets, and transitions from sealed back to open. POSIX socket and lock files use restricted permissions and inode-checked cleanup; Windows uses a named pipe. Unknown locks or endpoints are not removed to infer ownership.

Tickets represent responsibility that must survive preparation failure. Their state machine is `preparing -> bound -> granted -> started -> released`, with `unknown` preserving unresolved responsibility. An identity-free failed preparation remains readable as `unknown` only with a null native session and valid target, selection allowlist, requirements and scope; it cannot release or establish closure. Bind records the full execution identity, native session, original selection, cleanup requirements, and separate local transcript session reference. Only the original in-memory producer proof may register, bind, grant, consume, release, or mark tickets unknown. The authority never mints Owner receipts or directly closes the persistent leader execution set or releases organization capacity. Recovery-enabled services can attest original producer closure only from the full original receipt/drain path described below.

## Production Boundary

The production lifecycle starts the independent authority in `createDepartmentExecutionProducer.openNewLeader` and `openContinuedLeader`, before `ledger.open`; `src/extension.ts` supplies its directory under the trusted application data directory. `DepartmentLeaderExecutionLedger.admit` registers the complete responsibility with that authority before persisting the local execution entry or invoking preparation. It retains the authority ticket locally before awaiting IPC acknowledgement, so an ambiguous acknowledgement cannot silently erase responsibility. A producer configured with generation authority must supply register, bind, and consume hooks; there is no authority-backed local-only grant fallback.

Employee and leader admission bind the matching ticket to the persisted full binding, including employee `subtaskId`/`attemptId`, selection, cleanup requirements, native execution session and separate local transcript session. The final Owner grant path calls `authorizeStart`, which atomically consumes the expected ticket/claim over the original authority IPC before the bootstrap sends the grant to the actual Codex/OpenCode Owner worker. A seal that wins first rejects that consume. Each invocation owns an active admission until its actual `port.invoke` completes. OpenCode creates and invokes its first port within that admission, then creates a fresh admission and rebinds the same immutable responsibility/binding for each later round. Codex likewise verifies and rebinds its original binding for subsequent rounds. The authorization callback belongs only to that invocation; it is not cached as execution authority for future rounds. Ledger retains in-flight authorization IPC even if cancellation or terminal delivery returns first. A consumed launch remains inside the producer's retained admission promise, while native execution is sealed and drained by the original Owner; neither promise settlement nor authority state creates cleanup evidence.

Closing uses the exact original local scope/producer to irreversibly fence admission before awaiting IPC. Authority seal and original native seal/drain are both attempted, and retained pending work is awaited even if authority read, claim validation or persistence fails. An authority error remains a failure and prevents closure/capacity release; it cannot skip native cleanup. Only after all cleanup succeeds may current identity be revalidated and Ledger closure be persisted. A failed authority bind does not mutate the retained preparation into a locally invalid partial ticket.

## Round-428 original-service cold control

The original producer now registers recovery ports with the independent authority **before Ledger.open and the first pump**, using the trusted Owner directory and its inherited native-drain callback. Old version-2 services without these ports remain readable but reject recovery. `control`, `recovery`, `witness` and `retire` are strict version-2 IPC operations; no producer proof is persisted or returned to a recovery client. The advisory readiness file contains public state only; the original proof is delivered solely over the inherited parent IPC channel. `claim` retains its all-released restriction. An exclusive `controlId` obtains sealing/observation rights only; it cannot launch a successor. The service persists an irreversible seal before notifying the original lifecycle. Unconsumed preparation tickets become identity-free `unknown`, not absent or released.

Every original client retains an awaited cleanup witness. Before that client can retire its Owner endpoint, the independent service reads the exact original Owner over authenticated IPC and applies its full required policy. The service privately escrows that actual receipt, never a caller-supplied or disk receipt. The OpenCode leader facade forwards the witness to its actual original client. If the original host remains connected, its inherited callback invokes the existing Ledger/native/pending drain. If the host disconnects, the service can seal the exact original Owner entry; this does not prove host-owned tabs, consumers, roots or preparation clean. Only a complete set of actual required receipts plus original drain confirmation, or the complete original receipt escrow after disconnection, establishes the service's original producer closure. Missing/unprovable resources remain unresolved and retain capacity.

`DepartmentColdGenerationRecovery` is wired into explicit cold public-stop preparation after trusted route preparation. Before control or target restoration it verifies the persisted task, scheduler schema/plan, stored leader identity reader, original authority scope/producer, exact Ledger tickets/bindings, selection/config revision, requirements, employee attempts and native/local sessions. All candidates are checked before shared capacity restoration. Configuration and IPC waits use one absolute preparation deadline; authoritative task/root/capacity/set/bindings and request validity are reread after awaits. A competing control ID, drift, missing capability, endpoint loss or persistence failure cannot close or release an unknown group.

After the original service proves the full group closed, the recovery adapter persists the exact CLOSED with the existing store, then associates the verified **local transcript** through the existing session/tab manager; it never creates a replacement task or native session. Its stop lifecycle and cleanup observations are derived from that verified original group. `recoverRoot` keeps the original generation until original cleanup/capacity release; ordinary stop/continue owns the later generation transition. Warm stop's synchronous fence and independent cold-stop invalidation remain intact.

The existing organization path durably removes capacity before retirement. Only then may the original service close its own endpoint/lock. An ACK alone is insufficient: the client waits boundedly for that cleanup; component tests additionally verify natural child exit 0/no signal. An unforgeable in-process retirement capability transfers verified CLOSED/session provenance to the **new** producer; reads, file flags and newly constructed clients cannot mint it. Explicit continuation uses the existing scheduler and a new Owner/execution/generation, retaining the verified native session. Activation and stop do not replay a prompt.

Current supported cold continuation is Codex-only. OpenCode's retired canonical-directory capability remains private to the original lifecycle, so cold preflight refuses it rather than inventing a directory. Host-loss success is conditional on complete original receipts; this is not certification of arbitrary crashed-host tab/consumer cleanup. Production-component tests use independent real authority/Owner child processes, real stores and a new producer with no original producer/client memory, but controlled tab management and free deterministic Node CLIs. They do not replace installed-product/second-EH validation. Round-410 rejection, round-419 same-host EH, and prior failed reports keep their original scope. Full second EH, OpenCode cold provenance, unsupported live host resources, required platforms, final Git integration and final-tree regression remain open.


## Round-436 OpenCode original-source lifecycle

The round-428 Codex-only limit above describes that historical snapshot. Recovery-enabled original producers now register an OpenCode source with the same independent authority after the exact Ledger binding and before consume, while the original canonical execution directory still exists. `native-source` requires the private original producer proof, current claim, complete ticket/selection/native and local-session identity, an existing canonical directory, and no directory reused by another ticket. Nothing is inferred from a cold snapshot or caller path. Source state stays private to the original service; it is not a disk recovery credential.

The original client must first verify the full required receipt and await its original authority witness. Only after the actual private stopped handshake and directory retirement may the original lifecycle send `native-stopped`. The service requires its own escrowed receipt and confirmed directory removal. Producer closure waits for that acknowledgement as well as original native/pending drain. A stopped IPC failure rejects the retained completion barrier rather than silently losing responsibility. Concurrent authority receipt observations are coalesced per original ticket so endpoint retirement cannot invalidate a second in-flight observation.

A closed recovery response includes strictly validated OpenCode sources tied to all exact released tickets, complete selections and separate local transcript sessions. Legacy services without this field fail closed. Protocol version remains 2; the extension is strict and does not treat an older version-2 response as a source capability. A cold client cannot register or mark a source stopped, supply a receipt, or obtain producer proof. Original CLOSED, persistent capacity removal and confirmed original service retirement still precede the private one-use transfer to the new producer. Clientless OpenCode provenance is accepted only through this unforgeable transfer and still passes `assertRetiredOpenCodeSession`, source selection/attempt checks and the one-use move reservation. Explicit continuation uses a new Owner/execution/generation and canonical root with the same verified native session; it does not create a new task or replay on activation.

A second race exists in the original Owner client: another waiter can verify full cleanup and retire the endpoint before an already issued request returns. That late waiter now rechecks the same client's private validated completion after I/O, reapplies the exact required policy and witnesses, and honors cancellation. A new client, disk receipt, mismatched policy, or absent original completion still cannot succeed. The old round-428 log contains only generic stop rejection; it does not identify the failing resource. The controlled socket-delay regression demonstrates this source defect without claiming that the old log proves a particular endpoint's state.

Cold recovery caches retain compact task identity/routes/fingerprint rather than whole task histories or root copies. Concurrent preparation of the same root shares one operation. At most 64 pending preparations and 64 unresolved generation controls are admitted; uncertain controls are retained, never evicted to admit another generation. Failed retirement permits a retry of the same compact proof. Only confirmed original service retirement and accepted capability transfer delete the matching prepared/control entries; stale finalizers cannot delete a later generation.

Verification remains a production-component boundary: real original Owner/authority child processes, production stores/Ledger/cleanup and an independent new producer, controlled session/tab management and free deterministic CLI fixtures. The OpenCode successful host-loss case obtains full original receipts and directory retirement before disconnecting the original host channel. Unknown consumers/tabs/roots/preparations, old records lacking source capability, lost endpoints, drift and failed durable writes retain capacity. Installed OpenCode behavior, arbitrary host crashes, real second EH, necessary platforms and final integrated-tree regression remain separate acceptance gates.
