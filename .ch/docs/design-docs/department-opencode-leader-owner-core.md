# OpenCode Leader Process Owner Core

## Scope

This document describes the fixed-generation OpenCode leader process Owner and its production preparation path. The production host registers responsibility before preparation, holds the expected configuration revision while its private loopback server creates and verifies one native `ses_` session without a task prompt, persists and reads back that session, then atomically binds and reads back the exact execution before invoking the process Owner. The public Owner endpoint remains identity-only. The existing OpenCode parallel parser/consumer receives bounded output with separate run/process/message state for each leader tab. Native-session verification preserves each durable local transcript key; simultaneous leaders never share the primary one-shot controller.

## Runtime Contract

The trusted bootstrap receives a fixed preparation containing the exact leader identity, allowlisted CLI selection fingerprint, configuration lease directory, fixed owner directory, prepared command/arguments/environment/cwd, and the already-bound native session ID. It rejects unbound identities and mismatched session, role, CLI, or selection metadata. This object travels only over the worker's token-authenticated private IPC channel. The public Department Execution Owner socket continues to accept only its existing identity-scoped start, observe, and handoff operations.

One Owner is created for one immutable generation and one binding. Each invocation has a bounded immutable ID and prompt digest. An identical repeated ID returns the original promise; a changed prompt conflicts. A single invocation may be active at a time. Every invocation asks the trusted host for its own final grant. The authority check and one-use grant acknowledgement are synchronous with no intervening await; cancellation or sealing observed before that point denies execution. Once granted, the detached Owner owns the child through real process close, stdio drain, and output-consumer drain, even if the Extension Host disconnects.

Each run uses the existing OpenCode run-argument builder and `runCliProcess`, appending the same bound session ID. Trusted preparation rejects `baseArgs` containing `--session`, `--session=...`, `-s`, `-s=...`, or attached `-sVALUE` forms, so a preconfigured argument cannot override or duplicate the fixed binding. The shared builder retains its existing behavior for other callers. The bootstrap and Owner both cap a generation at 128 unique invocations.

The next invocation is not admitted until process lifecycle and the host's output consumer drain both complete. Sealing closes admission, waits for the active invocation, and aggregates process, stream, configuration lease, execution-root, link, overlay-temp, and tab facts. Missing required facts remain unobservable; receipt creation remains delegated to the existing Owner server and its cleanup requirements. Private-channel failure explicitly rejects every pending invocation and makes the generation unobservable; a previously granted child remains owned by its worker and is never retried under a replacement Owner. Every bootstrap close path shares one seal-send gate, including cancellation released by worker readiness; the worker treats a repeated seal as a protocol failure. Repeated close calls share one promise. The worker records admission closure separately from transport failure and receipt readiness; an early shutdown request waits for the persisted receipt before closing the Owner endpoint and acknowledging `stopped`. A receipt alone is insufficient for the bootstrap to report cleaned: only a receipt read by this bootstrap plus its observed `stopped` acknowledgement can produce `cleaned`. While close is pending or failed, and for an Owner observation that resolves during that interval, the bootstrap returns `unknown`; a server-side cleaned receipt without this bootstrap's completed handshake is also kept unknown. This retains the responsibility boundary across disconnect and close races.

## Native event directory and original execution root

OpenCode 1.19.5 local `run` subscribes to instance events filtered by directory and waits for this session's idle status. Session creation in the workspace followed by execution in a different temporary root can finish and persist an assistant answer while delivering neither stdout nor idle to the run consumer. Round-364 observed exactly this boundary; installed-source inspection and round-366's repaired real execution confirm the directory contract.

For production OpenCode leaders, Ledger responsibility is persisted first. The trusted host then creates **one** `createLoopSubtaskExecutionRoot`, retains its original inode/link cleanup closure, and canonicalizes its cwd with realpath. The private owned preparation server creates and GET-verifies the native session in this isolated root. Both native responses must identify that same physical directory. The preparation service independently closes and drains before task session persistence/readback and atomic Store binding/readback. The worker receives a private `hostExecutionRoot: true` capability and uses this already prepared cwd instead of creating a second root. Every generation invocation uses it, with the existing per-round configuration/binding/final-grant checks and a fresh original-root identity check. Directory/attach/continue/fork CLI overrides are rejected; the shared CLI builder is unchanged. Normal Loop+ root construction and employee preparation retain their prior behavior.

Sealing still waits for every physical child, stdio, overlay and output consumer. Only then may the worker request `release-root` over its authenticated, sequenced, identity-checked private channel. The host invokes the retained original root disposer; replacement directories, changed links or unexpected contents cannot be reported removed. The worker requires a confirmed root fact before releasing its generation config lease and asking for tab cleanup. Public IPC remains identity-only. Missing root capability, lost host, failed cleanup or unknown invocation prevents complete receipt and capacity return. Failed preparation retains its root capability and responsibility rather than authorizing another preparation. A host-owned root failure cannot be repaired with a replacement root or Owner.

Explicit continuation of a prior native session is **not** permission to create/fork a new session or execute it from a new event directory. The preparation helper uses GET-only for a bound ID and checks the original session directory against the owned isolated root before binding/grant. A previous-generation session whose root was removed, or a session in the original workspace, is therefore refused/observation-only; safe cross-generation native directory continuation and cold recovery remain separate gates. Same-generation rounds reuse the original root/session without another preparation.

Round-366 used OpenCode 1.19.5 with a free loopback provider: one native preparation and two naturally completed task processes on one Owner/session, production parser/native validator, independently drained preparation server, original complete receipt plus stopped, original root/link removal, overlay/config lease release and controlled tab close/readback. This is real binary plus production-component evidence, not a real EH/tab or full-tree capacity end-to-end claim. See the native-drain runbook for immutable artifact paths and platform limits.

## Example

```ts
const owner = createDepartmentLeaderProcessBootstrap(preparedBoundLeader, trustedHost);
const first = await owner.invoke({ invocationId: "main-1", prompt: "Inspect the change" }, signal);
const second = await owner.invoke({ invocationId: "main-2", prompt: "Report the result" }, signal);
const cleanup = await owner.closeAdmissionsAndDrain();
```

`preparedBoundLeader` is an in-process capability produced by trusted preparation, not a public command payload. Callers must not pass model-authored executable paths, arbitrary environments, or unbound sessions. The production host builds this capability from the fixed route, configuration selection, trusted CLI builder, and native preparation result; it does not accept those values over public IPC.

## Follow-up Gates

The production host now covers new process-backed OpenCode leader generations and same-session multi-round execution through the existing Loop+ leader injection port. Codex retains its existing transport. First preparation has a durable Ledger responsibility before any native work. Preparation is reserved once per scope; failed or unknown responsibility cannot authorize another POST or a replacement Owner, including after a host is reconstructed. The native preparation server belongs to this preparation and is joined through real close/stdio/overlay drain before releasing its preparation config lease. The fixed worker acquires and validates the same revision before any invocation, then retains its own lease for the generation. No configuration profile contents or prompt are placed in identity, binding, receipt, or logs.

The sole EH task writer persists the trusted native result and reads it back; the Store atomically binds the exact selection/identity and reads it back before worker creation. Task cold-read/write validation accepts only the matching frozen Codex/OpenCode leader route, requires real `ses_` syntax for OpenCode, and refuses replacing an existing native session. Local task/tab identity remains stable; the trusted parallel-consumer callback validates only the exact persisted native result and bypasses generic session adoption. Real department-created OpenCode tabs use the existing WeakMap capability and consumer completion contract.

Closure uses the original bootstrap observation capability, not a new raw socket client. The producer closes canLaunch before waiting; bootstrap readiness during sealed closure is therefore observation only and cannot require launch authority. Invoke and grant still require full authority. Only validated receipt plus `stopped` may enter group aggregation. The production cleanup policy accepts exact OpenCode leader bindings and retains its complete CLOSED-set, pre/post policy, original-client and final cold-read gates. This host never directly releases capacity; existing orchestration remains the sole durable-remove-then-return path. Unknown groups retain their bounded Owner/preparation references.

The integration tests use the real production producer, owned task repository/router, Ledger, atomic runtime Store, SharedRuntimeConfig leases, detached fixed Node Owner and real child lifecycle. Controlled free CLI and tab-host substitutes prove first task-session and binding readback ordering, two same-session invocations, preparation cancellation/root withdrawal, config lease refusal and stale revision, persistence-stage withdrawal, Owner loss, tab failure, original-receipt group aggregation, and original output drain after stop while later launches remain fenced. The transcript test exercises the existing one-shot parser with the injected Owner stream and stable local identity. Two additional adapter-port scenarios use its unchanged runDepartmentMain contract, the original read-only fixture and real production host to prove same-session rounds and cancellation before any task process. Only the adapter CLI allowlist expands; no scheduler/adapter protocol or shared fixture is changed. These are component/production-host checks, not real OpenCode binary/model or full EH evidence. Capacity release under the full OpenCode-leader scheduler tree, cold restart and Windows/Linux behavior remain unverified. Configured executable prefix arguments and custom thinking workspace files are conservatively rejected by the initial production entry; ordinary CLI callers retain their existing support.

The existing execution ontology is unchanged: this adds a production implementation of the existing leader Owner path without changing identity, receipt, capacity, or scheduling semantics. Whole-group receipt aggregation remains the existing downstream gate; this host does not directly release leader capacity.

## Parallel leader output repair (round 351)

The production OpenCode leader entry uses `runPromptParallel`, including its tab-local process map, output buffer, native-session check, persistence and completion status. The existing tab stop operation is hosted by the same runtime and used by the extension composition root. A stop marks only that tab stopped and requests termination of its original Owner invocation; the consumer promise still waits for the transport drain notification before finishing its tab capability. Stop status is not a cleanup receipt. Separate leader tabs can stream, finish and stop independently; no ordinary execution fallback or replacement session is introduced. Two controlled-transport regressions cover interleaved output/completion and cancelling one leader while the other completes. They do not prove real CLI/EH tab removal or physical drain, which remain responsibilities of the original Owner and resource contracts.

## Owned stream retry fence (round 353)

The shared OpenCode prompt template enforces the retry budget before recording, announcing, waiting for, or starting a failed-attempt retry. For `departmentProcessStream` the effective budget is always zero, even if a host failure evaluator returns retryable under the ordinary global budget. Both parallel and one-shot consumers use this fence. The same zero budget governs missing-conclusion recovery, so an empty successful exit cannot replace the bound session or replay the invocation. The original transport remains responsible for drain; cancellation does not finish its consumer until that transport settles.

Ordinary OpenCode calls retain their configured budget, recovered-reply counter reset, fresh-session recovery policy and command-repair restriction. Controlled tests cover retryable nonzero exits and errors with a positive ordinary budget, no retry wait/status/fallback, failure finalization, and another leader tab completing independently. These tests exercise consumers and policy, not real CLI/EH execution, physical Owner drain, capacity release or cold recovery. No Owner, binding, public IPC or capacity contract changes.

## Native output binding validation (round 359)

The production `departmentLeaderNativeSession` callback uses `createDepartmentLeaderNativeSessionValidator`, created once per invocation with its fixed local transcript key and config ID. Every native-ID report from stdout/stderr or final adoption reads the task's persisted `executionSession` and verifies the OpenCode CLI, exact native ID and config. The first successful validation pins one observed native ID; later replacement of the persisted ID cannot authorize a different ID within that invocation. Read failures propagate without pinning a new ID. State is local to the invocation, with no global cache or skipped binding reads.

This is read-only validation, not metadata persistence. The stable department task/local transcript ID, immutable persisted `executionSession` and existing atomic Owner binding provide the identity relationship. Ordinary `interactive/metaStore` supports Codex/Claude mappings only, and its disk writer absorbs errors; a void return from that port cannot prove an OpenCode mapping. This callback no longer calls that port or tracks fictitious write success. Ordinary mapping timestamps and error behavior remain unchanged. Consumers continue reporting IDs so later conflicts remain observable; Owner, retry, grant, tab, drain and capacity contracts are unchanged. Targeted tests cover the validator and production source delegation, not real OpenCode/EH execution or disk performance.
