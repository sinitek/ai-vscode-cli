# Department-Owned Task Source

`DepartmentOwnedTaskSource` provides a versioned, isolated task root with an explicit source id and canonical root. Registration leaves `.department-source.json` containing `{version: 1, sourceId}` as a durable root boundary. A missing marker can be created; a malformed marker, non-regular marker (including symlink, directory, or special file), or marker bound to another source id is rejected. Supported ordinary storage writers in other Node processes discover the marker by resolving the nearest existing parent once and walking its real ancestor chain, so directory symlink aliases remain within the boundary without scanning an in-process registry. Disposing a source never removes the durable protection. `claim()` creates `.department-owner.json` with exclusive `wx`; an existing or malformed owner marker is never taken over based on process state, elapsed time, or file metadata. The capability is an object identity plus random token and revision. Ordinary `tryWriteLoopTaskStore` and `deleteLoopTaskStoreFile` reject descendants before touching disk. Ordinary writes also reject an existing non-regular final entry. They publish through a unique same-directory stage file and rename, so a final-component symlink is never followed into a controlled root; ordinary directory aliases and normal Loop/Loop+ roots retain their existing behavior. Deletion uses `unlink` semantics and protects the link's containing path; it does not follow a final symlink to inspect or delete its target.

Owner transactions invalidate lifecycle subscribers before writing a durable `.department-recovery-<token>.recovery` snapshot, normalize through `normalizeLoopTaskStoreForStorage`, stage all replacements, then publish the files and revision. Successful commits remove stage and recovery files before notifying observers. Observer exceptions are isolated after commit. On any failure the source stays invalid, and a recovery snapshot blocks `prepareRebuild()`. An owner must explicitly call `recover(capability)` to restore the pre-transaction contents; a successful complete rebuild remains a separate step. Cleanup or restore errors retain invalid state and recovery material.

Enumeration is direct-child only. The owner marker and recovery artifacts are excluded by their non-task suffix/name. Matching `.json` symlinks, directories, and special files are rejected; `lstat` failure, unreadable root, or an entry disappearing during enumeration also aborts the complete listing. Reads use the shared storage normalization, but first validate every raw record; malformed records cannot disappear during normalization and produce a partial trusted snapshot. On explicit recovery, every file is restored before this capability's `.stage` and `.restore` artifacts are removed, and the recovery manifest is deleted last. A restore or cleanup failure leaves the source invalid and the recovery manifest available for another attempt. The caller must then perform a complete rebuild. Controlled roots must be routed through owner transactions for any future retention, migration, deletion, import, restore, or session/runtime rebind; ordinary APIs cannot perform these mutations.

`DepartmentOwnedSourceController` is the host-only composition boundary for the source and one `DepartmentOwnershipIndex`. `create()` requires a trusted asynchronous writer-quiescence barrier, claims the durable source marker, clears the source rebuild gate, and publishes readiness only after one complete index rebuild. It keeps the owner capability private and exposes token-free file, read, commit, recovery, rebuild, and close ports. A commit closes index authorization before entering the source transaction and performs at most one complete index rebuild after a successful durable commit. Failed commit or rebuild remains unavailable; `recoverAndRebuild()` is the explicit recovery route. Incremental source notifications cannot make an invalid index ready.

`commitSync(updates): boolean` is the synchronous host-router boundary. It shares the same transaction/publication implementation as `commit(updates): Promise<boolean>`, returns true only after owner persistence and index republication, and rejects without writes when unavailable or an operation is already active (including an accepted async commit awaiting its first continuation). It does not fake an async result or schedule background persistence. The async API keeps its admitted-operation drain semantics: a commit accepted before close can finish persistence, while reads stay revoked throughout close/barrier.

`readRevision(): number | null` exposes a process-local publication generation, never the owner token. It advances after initial successful publication and every successful commit/rebuild/recovery publication, and returns null when unavailable. `ready` additionally verifies the source's current owner marker. Repository caches bind to this generation; commits outside that repository or explicit rebuild/recovery require complete repository reinitialization. A host-wide authoritative identity catalog (including ordinary tasks) must also publish synchronously before the repository's commit closure returns; the controller's department index alone cannot prove absence of an ordinary identity. The controlled source reader and transaction normalization preserve expired records for complete initialization, identity and relationship checks. Public repository routes retain historical filtering; the ordinary reader keeps its default retention behavior.

`close()` synchronously closes admission, invalidates the index, waits for accepted controller operations, then awaits the required host-provided quiescence barrier before releasing the owner marker. A failed barrier leaves the marker in place and the controller unavailable. The barrier must cover every supported writer outside this controller; a CLI promise finishing or a stop request being issued is insufficient evidence of quiescence. This module does not itself establish that central production wiring covers those writers, and callers must not expose the controller or capability to a Webview/model.

Legacy global task files do not become trusted department records and require explicit identity-mapped migration with conflict checks. Automatic ordinary legacy migration preflights the published identity catalog before moving communications; an unknown imported identity, owned ID, unavailable catalog or ambiguous contribution is refused without those moves.

Production assembly now lives in `departmentProductionTaskStore.ts` and is mounted once by `extension.ts` at activate, under `~/.sinitek_cli/department-tasks-v1`. The private controller supplies the real source/index authority; null authority is no longer substituted for this dedicated source. Both director and leader are complete repository creations, never ordinary records promoted afterward. Public update/append/rebind/delete/retention route to the same owner. The factory binds readRevision and a synchronous `commitSync` closure; the persistent ordinary/department identity catalog publishes before that closure returns. Task IDs, sessions, and scheduling modes remain independent.

The catalog's durable `owned` map reserves each department ID at its original physical file even after logical deletion or retention. Hosts without an acquired source/router consult this classification before ordinary discovery or mutation; unavailable classification refuses fallback. These tombstones survive close/reopen and prevent a deleted department ID from being reused as an ordinary task. They are identity reservations, not proof that any execution has ended.

The production barrier is a check over actual supported writer admission: the controller/capability never escape, its only external write closure is synchronous and counted, and close first revokes/disposes that sole repository router before controller drain. Future runtime callbacks cannot use the old router to write. A pending identity transaction, unknown lock, partial catalog failure, unverified external writer or source recovery failure prevents owner-marker release. This barrier proves storage-writer quiescence only; it is not evidence that a CLI runner stopped or cleaned up. Runtime execution receipts remain a separate integration gate.

`revokeBeforeExternalChange` closes reads and writes before an unsupported import/restore/path move could publish, and deliberately prevents marker handoff without new writer proof. Existing unknown owner markers are never adopted; no-op barriers, watchers, process liveness, file timestamps and marker age do not authorize takeover. This version mediates supported ordinary low-level writers through the shared identity transaction gate even before catalog bootstrap, so initialization cannot overtake those writes. An arbitrary raw filesystem writer or an older binary bypassing this protocol is not covered. Such writers must not be declared coordinated; their import/restore remains unsupported. A damaged/uncommitted identity catalog is kept closed; production operator recovery is not yet delivered.

Central source registration and deterministic production-source/organization composition have implementation and unit evidence. True Extension Host/CLI startup, active execution handoff and cold restart remain unverified; an in-process close/reopen test is not cold-restart acceptance. Ordinary communication retention now reads durable department identities (including deletion tombstones) under the shared writer gate and holds that gate through deletion. This applies in a Node host without a source/router. A missing, locked, damaged or unpublished catalog skips all communication deletion; unknown identity never authorizes ordinary GC. Expired ordinary orphan artifacts beside a ready catalog retain their normal cleanup behavior. Owner-aware department communication garbage collection and tombstone reclamation remain separate work.

Production repository snapshots use `locateLoopTaskIdentities(ids)` for one current catalog read and one contribution traversal per group, preserving duplicate contributions and durable tombstones. No authorization cache outlives that call. The repository's source revision checks and complete relationship validation remain in place; the production source predicate no longer rereads the entire identity catalog around every record lookup. The legacy single-ID port delegates to this same implementation.

`scripts/verify_department_host_activation.js` launches the installed VS Code with a separate HOME, user-data/extensions/workspace and the current built product as a development extension, following the existing compaction smoke's Extension Host test entry pattern. It observes automatic `onStartupFinished` activation without calling activate or injecting a source, verifies source/owner markers and a ready catalog under the isolated HOME, then requires normal instance exit, owner release and no remaining isolated processes. Failures preserve logs/report; forced cleanup cannot count as success. The smoke submits no tasks or real CLI requests. macOS uses a short /tmp root to respect UNIX socket path limits; this does not prove cold restart, task restoration, real CLI cleanup or other platforms.

Round 102 local smoke evidence (macOS arm64, installed VS Code 1.144.0): the actual product activated via onStartupFinished and wrote its real source/owner markers and ready identity catalog to the isolated HOME. Extension Host deactivation released the owner marker. The standalone application main process did not exit even after the test requested quit; the smoke correctly failed, preserved logs, and forcibly cleaned up only its isolated process group. This is partial activation/deactivation evidence, not a passing whole-instance smoke or cold-restart acceptance.
