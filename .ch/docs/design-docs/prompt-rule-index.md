# 提示词规则索引方案

把插件维护的完整规则随 VSIX 分文件交付。每次 CLI 调用收到用户任务、本轮宿主事实、少量必须当场执行的约束，以及当前角色能用的一页索引。AI 按任务进展打开索引中的文件。验收标准、用户授权和调度门禁各自由原来的责任方判断。

## 现有接入点

| 入口 | 可复用的边界 |
| --- | --- |
| [Vibe 和 CLI 包装](../../../src/promptRuntime.ts) | `buildThinkingPrompt` 已按 CLI、输出和人机交互开关组装提示。索引由该层接入普通对话，Loop 决策沿原入口使用各自的输出协议。 |
| [经典 Loop](../../../src/extensionHost/loopOrchestration.ts) | 主任务和子任务分别构造输入。产研部总监已有独立分支和提示长度上限。 |
| [Loop+](../../../src/extensionHost/loopPlusPromptBuilders.ts) | 主决策和执行尝试分别构造输入。可从[本轮决策契约](../../../src/loopPlusDecisionContract.ts)派生状态、空槽与完成资格。现有决策助手负责生成和校验协议 JSON。 |
| [产研部角色](../../../src/departmentprompts.ts) | 总监从经典 Loop 接入。索引模式由 Loop+ 构造器选取组长或员工规则，`full` 模式由适配器使用原角色前缀。角色和容量来自宿主。 |
| [安装路径](../../../src/extension.ts) 与 [VSIX 导出审计](../../../scripts/export_vscode_extension.py) | 已加载扩展提供 `extensionPath` 给 Loop+ 助手。对规则资源采用相同的安装来源，在成品 VSIX 中逐项核对文件。`.vscodeignore` 已排除 `docs/`、`.ch/`、`src/`。 |

### 安装版读取实测

2026-11-28，在本机 macOS 的 VS Code 扩展注册表定位 `sinitek.sinitek-cli-tools` 1.10.6。当前 CLI 从工作区启动 Node，用同一组仅允许读取该扩展安装目录的权限完成三项操作。

| 操作 | 实际结果 |
| --- | --- |
| 运行安装版 `dist/loopPlusDecisionHelper.js template --status wait` | 退出码 0，返回含 `reportEventIds` 的字段模板。 |
| 运行同一脚本的 `build --status wait`，传入合成的报告回执 | 退出码 0，返回 `{"status":"wait","reportEventIds":["probe-report-1"]}`。 |
| 通过 Node 读取同包的 `media/workspace-scaffold/AGENTS.md` | 退出码 0，读到 6,785 字节，首标题为「仓库工作指南」，SHA-256 前 12 位为 `034fa009deef`。 |

因此第一版直接复用扩展安装路径和 CLI 现有读取能力。每轮给相关规则的文件名，AI 可以使用原生文件工具，也可以通过现有命令工具用 Node 读取。语义效果单独用真实任务验证，重点观察模型是否在检查失败、依赖变化或新增界面交互时主动找到对应规则。

当前工作树的一个可比样本使用「列出仓库入口文件。」、`split`、并发 6、系统默认验收方案、空队列、示例路径、有决策助手、省略可选路由摘要。按 JavaScript 字符串长度，从 `Rules:` 起到 `Decision helper:` 前计 **31,427 / 46,696（67.3%）**。上轮样本为 **31,590 / 46,888（67.4%）**。在相同测试构造器中，把回合换成仅有一条报告、没有运行任务，唯一候选动作已是 `wait`，仍发送 **31,426** 个规则字符。后者适合作为首个迁移样本。

## 规则文件如何归类

随包交付以下 29 份规则。每项描述适用场景和操作要求。多个角色共享的规则使用同一个文件。

```text
media/prompt-rules/
  manifest.json
  common/       direct.md  evidence.md  handoff.md
  vibe/         interaction.md  progress.md
  loop/         main.md  dispatch.md  worker.md  blocked.md
  loop-plus/    dispatch.md  review.md  repair.md  dependencies.md
                report.md  controls.md  closeout.md  blocked.md  attempt.md
  department/   director.md  leader.md  employee.md  collaboration.md  continuity.md
  topics/       ui-handoff.md  git-delivery.md  asset-license.md  summary-svg.md
  examples/     mixed-review.md  coordination.md
```

`manifest.json` 声明稳定 `id`、读取时机 `when` 和可选依赖 `needs`。安装相对路径为 `<id>.md`。构建为清单和全部正文计算 SHA-256 并记录在 `dist/prompt-rule-version.json`。加载时匹配摘要，校验实际路径、唯一 ID、非空正文和依赖关系。每轮索引按角色和宿主状态选取、补入依赖并去重，标出「必读」或「按需」。成品审计逐项对比包内正文与构建来源。

各入口从已有的 `reportOnly`、`allowDispatchBeforeReview`、冻结批次和验收方案等事实选择条目。模型根据条目里的简体中文条件补读，例如「派发事项会改变用户可见的布局或交互」。用户项目沿用工作区规则。任务 ID、用户请求、补充需求和沟通文件路径由当次调用传递。

| 场景 | 默认可见规则 | 根据任务再读 |
| --- | --- | --- |
| Vibe | 当前 CLI 的输出约定、必要的任务列表格式、已启用的人机交互入口 | 遇到实质性用户决策读表单细则。选择用图解释结果时读 SVG 细则。 |
| 经典 Loop | 主任务拿轮次协议与当轮派发条件，子任务拿自己的任务、交付与汇报规则 | 拆分、后续轮次、收尾按角色和阶段展开。经典 Loop 的 `continue` 和子提示长度约束限于适用入口。 |
| Loop+ | 主任务拿当前许可动作及冻结范围，执行子任务拿自己的目标、边界、交接条件 | 验收、返工、依赖、控制各自有入口。`split` 或 `fullstack` 只展开本次路线。 |
| 产研部 | 总监用经典 Loop 的协调协议并按汇报判断业务结果。组长用 Loop+ 主规则并继承根验收方案。员工用 Loop+ 执行规则并向组长汇报 | 分配工作时看参考额度，跨组请求时看协调规则。总监的授权限定在协调和汇报，独立验收归组长。 |

`topics/` 适合放 UI 状态与主题交接、Git 授权交付、素材许可证、总结画图等长说明。宿主知道用户选了专项验收时，直接提供该项要求和用户原文。AI 在分析或读代码后才发现涉及界面交互时，也能通过当前角色的专题索引找到 UI 交接要求。索引按语义写触发条件，任务标题中是否出现 “UI” 或 “Git” 不决定读取资格。

`departmentCollaborations` 的填法归入产研部协调规则。总监按真实组长 ID 和可用名额协调，跨组业务例子单独放在 `examples/coordination.md`。普通 Loop+ 主审只收到本任务的调度协议。

## 每轮如何发送和读取

1. 宿主先固定模式、角色、本轮阶段、可用动作、用户要求与授权、验收方案、冻结的事件和报告、当前容量及报告位置。任务状态只使用这次请求的快照，较晚事件由后续决策处理。
2. **直接给模型**角色边界、输出契约和影响本轮选动作的条件。例如 Vibe 的结束标记、Loop+ 冻结批次的顺序、报告回执的含义、组长的独立验收职责。每个条件写一条可直接执行的短句。
3. **给模型索引**以便其自主补读。宿主已知本轮必须适用的条目标为「本轮必读」。要由模型结合交付内容判断的条目写出触发条件，例如「任一交付检查失败时读返工规则」。模型可在读报告、检查代码或发现依赖后打开文件，也可合并一次读取。宿主依据最终提交的字段、冻结状态及原有门禁复核决策，真实任务对照验证模型判断质量。
4. **从已加载的安装目录读取**。`context.extensionPath` 定位 `media/prompt-rules/`，索引给出一个绝对根和各项相对路径。CLI 可用原生文件工具，也可沿用运行决策助手的命令工具。用 `sinitek-cli-tools.promptRuleDelivery` 选择传递方式并重载窗口。`indexed` 在本地发送索引，远程窗口采用 `inline`。`inline` 首发附上本轮所选各项正文。`full` 调用原完整构造器。安装资源缺失或摘要不符时自动走 `full`。
5. 普通交互与 OpenCode 收到本轮索引的精确 `RULES_UNREADABLE` 回执后，在同一执行中补发一次所列正文。一次授权的员工执行首发附正文。组长由宿主续接原有调度，Loop+ 协议纠正用冻结批次、正文和本轮合法形状。构造每个新模型请求时根据当时角色和快照给出索引，已生效的写入和调度以宿主记录为准。

文件路径使用宿主操作系统的路径 API。内联读取限于当前安装清单。用户项目、报告与运行数据按任务范围和既有权限查阅。实际报告或产物读不到时，相关验收项标为未验证并说明原因。修改规则时同步核对完整构造器、规则文件、冻结契约和回归用例。

下例展示混合验收轮的索引读法。实际根路径、任务、报告位置和决策助手入口由宿主提供。

```text
模式 Loop+　角色 主审　阶段 冻结验收　验收前派发窗口 关闭
冻结顺序 [e7,e8]　待回执 []　e7 执行失败　e8 执行完成
可选动作 accept / blocked / clarify　规则根 <本轮已验证的规则目录>
先读两项执行报告并检查交付。保留冻结顺序，分别给出证据。e7 不能判通过。
本轮必读  loop-plus/review.md    固定六项检查、已选验收项、全撤销例外
本轮必读  loop-plus/repair.md    e7 执行失败，核对原 ID 返工、免返工理由及独立项归属
按需读取  loop-plus/dispatch.md  还有可立即并行推进的独立交付时读
按需读取  topics/ui-handoff.md  新派发事项涉及界面布局、状态或交互时读
按需读取  loop-plus/blocked.md  已检查剩余需求且没有安全推进路径时读
```

同一任务切到纯报告回合时，换成一条指令即可表达本轮动作。「读指定 attempt 报告，判断其结果对剩余工作的影响，按本轮 FIFO 原序返回 `wait` 和全部 `reportEventIds`。本次仅确认报告已读，原冻结验收批次留到后续回合。」这一回合通常需要读取执行报告，规则文件读取可以为零。

普通 Vibe 用户问「这个按钮为什么一直是灰的」，模型通常直接查代码解释原因。若用户接着要求改交互，而且排查发现要处理禁用、加载和失败三个状态，模型就按专题索引读取 UI 细则。这样，规则选择可以随调查所得的新事实变化。对于已选的用户体验专项验收，宿主在对应验收轮直接提供它的原文和结果要求。

## 迁移时如何保住规则强度

为每个旧条款登记原位置、触发条件、责任角色、强制程度、例外、目标文件、宿主校验和正反用例。目录按角色隔离，规范正文只维护一份，字段枚举和合法状态取自现有契约。先做原文等价搬迁，再逐项合并。冲突以当前解析器、调度器及设计契约核对，行为分歧单列测试。

| 旧文中的实际问题 | 新版条文或落点 | 回归观察 |
| --- | --- | --- |
| 并发拆分、回填空槽、避免凑数在多条重复，另有仅派返工或空留槽位时写主沟通文件的要求 | 合并到 `dispatch.md`。「逐项核对原始和补充目标，按可独立交付的边界并行。扣除运行和即将获槽的排队项，在空槽与单次上限内派发有必要的工作。仅派返工或留下可用槽位时，在主沟通文件记下具体依赖、冲突、已占容量或无其它就绪交付。」 | 相同快照分别给有独立工作、已有任务覆盖和真实写冲突，核对派发集合与沟通记录。 |
| 同 ID 返工和独立项归属在固定正文和各冻结事件的示例里重复 | `repair.md` 只写一次二选一。每个失败项恰好一个原逻辑 ID 返工并复验，或给出有证据的 `noRepairReason` 并保留失败。每个新增项恰好归属一个事件或独立清单。宿主逐项提供真实 ID。 | 混合通过、失败、撤销。独立项不继承失败会话。单项失败不能带偏其它项。 |
| 「当前轮只编排」与简单任务直办同时存在 | 在主角色入口限定范围。满足低风险、直接可核实等条件的独立小事可直办。`allowDirectCompletion` 仅控制简式收尾，还要满足全部要求、宿主门禁及用户/项目验证要求。 | 队列非空时直办独立补充事项后继续原任务；需测试或已选专项验收时走对应验证。 |
| 「开批且有新消息一律禁止 dispatch」与一次性验收前窗口冲突。「wait 什么都不确认」与纯报告回合冲突 | 以冻结契约选择条文。窗口开放时才有一次带 `nextStepPlan` 的验收前派发，全部独立项须能立即启动，本批保留。窗口关闭走验收路径。纯报告 `wait` 按原序确认报告。 | 分别开关窗口并加入新消息。没有运行项时提交报告回执，验收队列保持原样。 |
| 只读 `general` 的 `writeFiles` 与「每个子任务填 writeFiles」冲突 | 写入提示适用于写任务。新生成的 `general` 省略 `writeFiles`、`codingDelivery`。 | 定向调用当前实现，省略时助手与解析器均接受，`writeFiles: []` 时助手拒绝、原始解析器接受，非空写路径时两者均拒绝。保留兼容输入与新生成规则的区分。 |

验收正文保留每项交付独立判断、六项基线与已选附加项、全撤销例外、未核实项的处理、复用有效证据和失败返工。`dependsOn` 的执行准入与已交付后继的验收顺序各自保留。模型负责判断证据是否覆盖需求、是否还存在独立工作和授权边界。解析器、决策助手和宿主分别继续约束字段、冻结批次、会话归属与最终提交。

## 验证结果

使用 `npm run build` 和 `node scripts/verify_prompt_rule_index.cjs` 可复测。表格按 JavaScript 字符串长度计数。`Rules` 从 `Rules:` 开始，到 `Decision helper:` 前结束。“整条输入”指 Loop+ 主决策构造器生成的文本，含任务、快照和助手说明。实际数值随目录长度、任务内容及选定验收项变化。

| 合成的 Loop+ 回合 | 完整版 Rules | 索引版 Rules | 降幅 | 完整版整条输入 | 索引版整条输入 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 首次决策 | 31,426 | 2,055 | 93.5% | 46,889 | 3,203 |
| 仅有免验报告 | 31,426 | 365 | 98.8% | 43,523 | 1,464 |
| 单项冻结验收 | 32,986 | 2,485 | 92.5% | 48,651 | 3,855 |

`node scripts/verify_prompt_rule_index.cjs --live` 使用真实 CLI 和独立的临时目录配对检查同一个交付。执行报告声称交接清单已写明发布负责人和回退命令，实际文件只有负责人。两版均判定失败，按原逻辑 ID `handoff-document` 发起需复验的返工，通过冻结输入解析。索引版的成功工具输出中出现了验收、证据、派发、返工四份规则的正文。另一次从 VSIX 解包目录运行纯报告场景，模型读取两份实际报告，通过包内助手生成 `wait` 和原序的 `["r-z","r-a"]`。

| 同一验收用例的配对 | 完整版 / 索引版工具调用 | 完整版 / 索引版耗时 | 完整版 / 索引版累计输入 token（含缓存） |
| --- | ---: | ---: | ---: |
| 初次搬出正文 | 7 / 13 | 207 / 123 秒 | 196,826 / 250,379 |
| 合并派发、验收、返工及证据的重复条款后 | 7 / 12 | 94 / 179 秒 | 218,944 / 166,865 |

第二组中缓存输入分别为 179,160 和 144,896。中间曾有一次判断正确但缺少返工文件的读取证据，随后在验收条款写明发现漏项时必须先查 `loop-plus/repair.md`，并改以工具成功输出的正文核对读取。最后对独立直办例外的措辞调整让首轮与验收轮各增加一个字符，已计入字符表。当前样本支持对发送长度及这两个执行场景的结论。所有模型、平台和模式的端到端成功率、耗时中位数与 P95 仍需更多配对样本。

构建、903 项相关 Node 回归、22 项打包工具测试、9 项 ontology 测试及隔离的 macOS Extension Host 激活通过。最终通用 VSIX 内的 29 份规则及版本摘要逐一通过审计，解包到含中文与空格的目录后成功加载。详细命令和交付范围见[实施记录](../exec-plans/completed/2026-11/2026-11-28-feature-prompt-rule-index.md)。
