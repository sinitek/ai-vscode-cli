# Loop / Loop+ 宿主中断后的完成回报

## 恢复边界

VS Code 或扩展宿主意外退出后，原控制器、等待 Promise 和 CLI 进程句柄均不可继续使用。任务记录、会话消息、子任务沟通文件以及 Loop+ 调度快照是恢复依据；不接管崩溃前的外部进程，也不根据文件内容猜测成功。

群聊编辑器以工作区和完整任务 ID 定位原任务。缺失绑定时由用户从当前工作区的候选中选择。绑定属于其它工作区或格式损坏时拒绝恢复。已有绑定暂时读不到时可重试，选中的任务在展示前仍须从受控来源重读。恢复页面与发起执行是两次独立操作。

普通 Loop / Loop+ 的交互式主调用取得原生会话 ID 后，按原运行记录版本持久化会话绑定。主任务第一条助手回复尚未出现时，原生会话和对应的主任务消息仍能证明身份。显式续跑复用这个会话。主标签缺失时可用已存的会话重建。早期任务缺少会话字段时，按最新的同任务主执行记录与相应会话消息交叉核对，身份冲突时拒绝建标签。组长须通过原工作区、组长会话、主角色消息、标签占用及部门运行权限的验证。

任务身份目录的 `transaction.lock` 记录本机作用域摘要、持锁 PID 和随机代次。启动、获取写锁遇到竞争或用户重试原任务时，只有本机作用域一致且 PID 探测返回 `ESRCH` 才尝试回收。回收者先取得该代次的独占权，再核对文件内容与文件身份。旧版空锁、权限未知、活进程或其它机器的锁均保留。移除已退出进程的锁后，读取仍须通过目录已提交校验。

`isLoopTaskRunOrphaned` 以当前宿主的真实所有权判断失联，持久化的 `activeSubtaskIds` 不再证明进程存活。运行核对将失去所有权的 running 主任务记为 stopped，并持久化 `runtimeInterrupted=true`；保留活动 ID、Loop+ 原快照和待验收队列，把 running 子任务标为 blocked。用户主动停止清除该标记，并继续走原停止策略。

部门组织根是该普通运行核对的例外：本地 `runningTaskIds` 只证明本宿主的模型调用，不证明原组织责任完成。经原部门仓储、精确 root/总监角色/parent/module 和当前 workspace 校验的根，不因本地调用缺席写 stopped/runtimeInterrupted 或改动子任务。已经被旧核对误写成 stopped 的根，只要原容量未核验归还（或读取仍未知），仍在原工具栏位置提供组织停止；沿用原 `organizationControl.stop`，不伪造本地运行者或启动主模型。停止未完整返回（包括容量归还后等待原服务退役）及停止失败期间不提供继续；异步继续失败的 settled 回包也不能重新启用继续。完整 required receipts、精确 CLOSED、持久容量归还和原服务退役仍由原链路验证，状态读取不替代这些事实。非法或跨工作区记录不会取得该组织操作能力。

重新打开不会自动执行任务。用户可在原子任务 Tab 手动继续；完成结果必须来自本次成功运行记录。原记录没有该标记且已经 stopped 时，无法可靠区分历史用户停止与旧版本的状态核对，不猜测恢复原因；应显式继续父任务。

Loop+ 群聊继续按钮区分控制器所有权与主模型调用：控制器可以仍在等待子任务或调度事件，而主模型已经空闲。此时按钮将继续文本放入 Loop+ 用户消息队列，复用对话输入的唤醒路径；切模型先更新运行时提示与模型路由，再排入继续消息，避免用缓存模型抢跑。若没有当前控制器，则显式重建原调度快照。真实主模型调用忙时不重复启动；继续仍保护失败上限、完成状态和无效快照。群聊“继续执行”和“切模型”共用子任务恢复协调器，继续执行在原配置恢复成功后自动恢复中断子任务，保留模型、配置和思考力度。经典 Loop 等待恢复子任务及原控制器安全收尾后再继续主任务，回调不重复恢复子任务；Loop+ 复用原开放 attempt，继续说明进入现有用户消息队列。没有可恢复子任务时沿用主任务唤醒路径。经典 Loop 仍按宿主所有权保护。此入口是用户主动续跑，不会在重新打开时自动执行任务。

### 启动前共享配置锁超时

历史普通 Codex Loop+ 父任务若在启动前因 `RUNTIME_CONFIG_LOCK_TIMEOUT` 达到失败上限并停在 `needs-review`，可以从原任务群聊手动续跑。已有结构化错误码须精确匹配。没有错误码的历史记录须精确匹配原固定消息。配置服务现行采用无锁契约，旧错误码仅用于识别已有暂停。

按钮投影与宿主受理共用资格检查：原工作区、任务、CLI、会话和配置身份必须有效，快照必须可由调度器读取且没有开放运行预留；主动停止、完成、等待澄清、会话忙或部门归属一律不适用。

宿主通过进程内队列应用原档案并保留 runner 指纹隔离。宿主在同一次 `withThread` 使用权内确认已加载原线程，或校验 `thread/resume` 回执中的确切原线程 ID。回执缺失或不符时拒绝发送。专用显式续跑沿用 `preserveLoopOrigin`、`resumeTaskId`，在未发布的调度副本中准备首轮提示、冻结验收批次和子任务预留。序列化首个 `turn/start` 后，同步重读原物理任务并复核身份、快照、状态、原任务档案标识、标签与会话空闲；将继续说明、失败重置、队列与预留一次原子替换到原记录，确认后立即在同一线程发送。只有已保存的预留才可启动；发送后登记运行，刷新和附加通知不参与提交、不拦截首轮。

写入失败、提交前取消、占用或身份变化保留原记录、计数、冻结验收、报告和待派发，不登记运行、不发首轮或子任务，不进入自动重试。已提交后的首轮发送或回执错误保留原错误，按实际执行失败处理，不自动另起线程，不回滚原子替换。线程使用权在首轮调用收尾或未启动清理时释放。普通同档案更新、其它入口及部门 Owner 门禁不变。

## 提交失败与展示刷新失败

恢复依据是已成功提交的任务记录。write 正常返回代表原子替换成功，I/O 失败传播，update 缺失任务返回 null；Loop+ 编排将 null 同样视为失败。提交之后的面板刷新失败只记录展示错误，不撤销已提交状态，也不重新执行任务。详情见 [提交与展示交接契约](loop-plus-scheduling.md#提交与展示交接契约)。

最终 completed 提交失败时保留控制器及显式 completionPatch；同宿主继续只补交最终结果，成功后完成通知和释放只执行一次。子任务汇报提交失败保留 error 暂停、原 attempt 事件/摘要与 Tab，不放行成功压缩或关闭；恢复磁盘后沿原显式继续路径提交事件，不重复启动 attempt。

宿主在提交成功结束的调度事件之前，通过原有任务更新端口保存绑定原子任务与 attempt ID 的结构化回执；部门任务仍服从 Owner 事务。事件和暂停提交均失败后，重建宿主只从已提交回执恢复仍匹配的运行预留，以原事件 ID 进入原验收或报告队列，和快照一并清除回执。不重复启动原 attempt，不重放通知、压缩或关页，也不代替主任务验收。父任务停止与冷宿主停止对账交错时，仍仅结算同任务内唯一且精确匹配的开放 attempt 回执；保留 stopped 门禁，不启动或准入 CLI，未启动的 pending 保持待派，仅显式续跑后再按既有调度规则处理。拒绝结算时原子保留已提交回执，不先消费；成功时与停止快照同一任务更新中清除。回执本身也未能提交且无其它已提交终态时，开放 attempt 保留为 blocked 并说明结果不确定，需核对产物并显式续跑或主任务处理；不得从 CLI 文本或沟通文件推断完成。

默认只读查询保留容错行为，读到空集合不能作为提交可成功的依据。`updateLoopTaskRecord`、`appendLoopRound` 和会话/运行目标绑定的来源查找、缓存读取、最终来源读取及目标合并读取使用严格契约；当前任务目录的冷查找也严格枚举和读取。只有 `ENOENT` 算缺失，其余 I/O 错误原样传播；JSON、任务容器或记录无法可靠归一化时，在写入和来源清理前拒绝。冷提交可能因其它候选不可读或损坏而保守失败，不等同于任务不存在。legacy 迁移和 retention 清理也严格读取，但在各自维护边界记录并包含错误，保留出错原文件，不将未知内容当空集合覆盖或删除。

改绑先通过 `path.resolve` 比较规范化路径，再按文件系统 dev/ino、realpath 判断身份，兼顾相对/绝对路径、点段及实际卷的大小写语义，不按平台盲目统一小写。同文件别名只提交已知来源位置，保留同文件中的兄弟任务，不执行迁移清理。真正迁移先严格读取并合并目标、提交目标，再清理来源；目标提交失败保留来源原字节。目标已提交而来源清理失败属于提交后维护，仍返回真实已提交结果并缓存目标；不会把更新报告为失败，也不从旧来源重试更新。

普通 update 和 append 的 `updatedAt` 不回退；真正迁移将目标时间戳推进到严格晚于来源及已有同 ID 目标，按 ID 冷查询和枚举去重选择较新副本。legacy 目标不存在时写入；目标已存在时，只有来源 `updatedAt` 严格较新才覆盖，相等或更旧均保留已提交目标。legacy 每项提交后使位置缓存失效，来源清理失败后枚举仍可重试，暖/冷查询保持已提交状态；同毫秒或时钟回退不能让残留旧来源覆盖 completed、摘要和轮次。普通残留副本沿原 retention cutoff 过期。低级按文件读取仍可能看到旧物理副本，不能作为跨文件权威查询。

存储保持同步接口、现有 JSON 外形、历史归一化、completed 防回退、会话绑定与 retention 语义，继续复用 `writeFileAtomicallySync`，不先删除目标规避原子替换。回归入口为 `src/test/loop/loopTaskStorePersistence.test.ts`；大小写敏感行为使用文件系统身份替身验证，不代表原生敏感卷或 Windows 已验证。存储接口不提供跨进程写合并、多文件事务、外部并发换链或 fsync 级断电保障。

验收已提交、后续修复派发被拒绝时，恢复和纠错使用最新快照，仅补剩余派发，保留 failed 判断、已接受任务及已确认消息。不得重放旧 accept；纠错仍受原协议次数上限约束，不新增巡检或全批屏障。

## 宿主仍存活时的等待巡检

扩展激活时注册 `loopWaitWatchdog.ts` 共用时钟，每分钟检查 Loop / Loop+ 子任务执行所有权并刷新已打开的群聊面板。Loop+ 的 `checkInterruptedMainTasks` 和 `checkWaitingMainTasks` 同时按分钟调用，原等待调度保留五分钟兜底。各检查独立运行，扩展释放时清理时钟。

子任务巡检按本宿主当前调用身份与 attempt 核实真实活动，不以任务记录里的 `running` 状态代替进程证据。确认失联后交回原主任务检查现有汇报和产物：可能验收已有成果，也可能沿原任务身份继续，进程退出本身不代表成功。经典 Loop 保留活动同级与批次门禁；Loop+ 将可关联的开放 attempt 送回原验收队列，真实 `failed` / `stopped` 仍按既有规则处理。主动停止、准备交接、隐藏重试和收尾不作为失联证据；旧运行的迟到回报不能覆盖新 attempt。恢复只针对当前宿主持有的任务，不冷启动宿主重启前的任务。

验收巡检检查本宿主空闲的 `running` 主任务是否已有未确认验收事件；即使还有子任务在执行，也能按正常事件入口补唤醒。主回合进行中、正在等待意外退出续跑、暂停、中止、澄清或完成时不补发。仍受前置约束的后继不进入验收批次；若已判定所有待审项均依赖阻塞，且调度快照未变，不重复挑选或写盘。

仅当前宿主持有的普通 Codex Loop+ 主任务，在已发送的回合以 `CodexUnexpectedTurnExitError` 结束后，才会登记原回合请求。巡检在该控制器空闲时领用请求，发送前再次复核当前工作区、原任务仍为 `running`、原主 Tab 仍打开且绑定原本地会话和原 Codex 线程。切换到其它 Tab 不等于关闭原 Tab；也不会另开 Tab 或线程补跑。启动前失败、未知退出、跨宿主遗留任务、经典 Loop、子任务、部门归属任务、手动停止、失去所有权、阻塞复核、暂停、等待澄清、完成或已达到失败上限均不具备资格。

AI 面板和群聊的用户中止先使本宿主排队及准备中的续跑失效，再取消调用；在停止记录上分别持久化 `userStopSource: "ai-panel"` 和 `userStopSource: "group-chat"`。写盘失败也不重新放行当前宿主的续跑。该标记区别于失去执行所有权时的 `runtimeInterrupted`；显式继续可以清除上一段运行的用户中止来源，不清零自动续跑失败计数。

首次意外退出只建立续跑资格。已经通过发送门的自动续跑再次以该异常结束时，持久化的 `loopPlusMainRecoveryFailureCount` 才加一。计数前两次成功记账后等待下一次分钟巡检；连续第三次将计数与 `needs-review` 一并提交，停止自动续跑。计数写入失败时不再自动发送；已发送的续跑若退出原因未知，则暂停并保留原计数。

任一子任务实际提交为已验收且通过（`reviewed` / `passed`），或无需验收的成功报告确认成 `reported` 时，计数与调度快照同次提交清零。主模型普通决策、子任务执行结束、报告仍待确认或验收失败不清零。宿主重建保留计数，但不会继承原宿主登记的自动续跑资格。

真实执行状态来自 Tab 的宿主运行所有权，不能仅依赖 `activeSubtaskIds`、未结束的 Promise 或 scheduler running 预留。准备启动、来源/会话锁、后台压缩、重试和收尾仍算活动。刚开始调用的 5 分钟内保留启动交接宽限，避免在 runner 建立所有权之前误判；已有活动兄弟或手动续跑也阻止恢复。

经典 Loop 保留本批等待上下文，正常成功仍立即推进；中断或失败则保持等待至巡检。若已无活动子任务，放弃失联 Promise、解除本批活动 ID，把尚未完成的子任务保留为 blocked，并将父任务标记为 `stopped` + `runtimeInterrupted`，使群聊“继续”可以重新执行这些子任务。原等待控制器继续存活；续跑成功后全部完成时立即交还，不另启主任务，也不等待下一次巡检。旧调用接收取消信号，来源/会话锁及时释放，迟到 resolve/reject 被消费，不能再写轮次、完成报告或重试；恢复后的提示只把确实完成的子任务列为已完成。主动停止不带中断标记，仍按原路径结束等待。

普通 Loop+ 主任务等待且运行中、修复中、验收中均为零时，分钟巡检核对本地控制器、父任务身份和权威调度快照，将系统补充需求与 `userMessageQueue` 同次保存。主任务在保存成功后串行接收消息，主沟通记录和群聊注明来源。同一提示复用已有记录，提交遇到竞争时由下一次巡检重试。父记录为 `running` 且身份、快照均匹配时，提交一并清理上一段运行遗留的 `runtimeInterrupted`。宿主重启后仍由显式继续取得控制器。

子任务中断后保留开放预留，准备启动、执行收尾和手动续跑均计为活动。补充需求列出中断的逻辑 ID 与 attempt。主任务按当前报告和产物确定接续点。用 `controls.reprompt` 可沿原逻辑 ID 创建新 attempt，宿主优先续接相容会话，缺少可复用绑定时新开会话。有后继依赖原 ID 时沿原 ID 续派。需要新 ID 接替时在 `dispatch` 或 `accept` 内同时关闭旧预留并派新任务，按同一份快照保存。接替准入或保存失败，原预留继续开放。

主决策中有待处置的中断项时直接 `wait` 会触发有界纠正。纯报告回合先确认冻结的报告前缀。主任务可在同级冻结验收的 `accept` 中处置中断项，批次之外新派的接替任务归入 `independentSubtaskIds`。验收完成后仍有当轮看到的中断项，主任务紧接着处理它。宿主提交控制时复核原 attempt 和执行所有权，已经手动续跑的成员保留当前执行。无开放子任务时，主任务仍可依据当前交付和验收条件收尾。

主任务 stopped、needs-review、error、completed、等待澄清或达到主模型失败上限时不自动唤醒；用户停止和异常恢复仍有不同语义。本机制不是子任务执行超时，不限制仍持有真实执行所有权的长任务。

## 经典 Loop

子任务进程只有在真实生命周期确认退出、结果仍未被当前调用消费，并跨过一个 60 秒巡检周期后才判定失联。OpenCode 隐藏重试会先消费前一次进程结果，再进入退避和新尝试；因此进程退出不是任务结束或失联的充分证据。

自动重试耗尽后，最终一轮的 CLI 错误进入子任务记录、沟通记录和群聊；巡检暂停时，将本批的实际错误附入主任务暂停说明。主模型仍需判断是否返回 `blocked`；若确认阻塞，持久摘要保留当前的子任务诊断。后续执行成功不再把此前的失败作为当前原因。保留现有重试次数、巡检及显式续跑，不把手动停止或失联当成 CLI 抛错。

手动续跑成功复用 `finalizeLoopSubtaskRun`：持久化子任务状态与摘要、写沟通记录、通知群聊；汇报成功后先清理完成时捕获且身份仍匹配的旧子任务 Tab，再按原条件后台压缩子会话。关页不等待同会话的前序压缩，压缩本身仍按会话串行；失败或跳过不影响关页。汇报失败则保留 Tab，不放行成功压缩。主任务恢复不等待后台压缩。活动兄弟任务未完成时保留等待状态；全部活动任务完成后，允许恢复带宿主中断标记的父任务，再继续主任务协调。

最后一个子任务清空活动 ID 与主任务启动之间，关闭标签可能触发面板运行核对。该核对同样保留宿主中断标记，因此不会让随后唤醒失去资格。按父任务 ID 保留唤醒中的内存互斥，避免并发完成回调重复启动主任务。用户主动停止、完成或主模型失败限制仍阻止自动唤醒。

## Loop+

`notifySubtaskContinuation` 在缺少内存控制器时可接收原主任务目标及输入，从任务记录重建调度器。只允许原任务仍 running 或带宿主中断标记的 stopped；拒绝已完成、主动停止、主模型失败限制、非法快照、parentStopped 或不存在的开放 attempt。

恢复时先注册控制器，再发布运行状态，避免状态刷新在交接间隙再次判为失联。原开放 attempt ID 不变，其余失去句柄且无可信完成回执的 running 预留保留为 blocked，供手动继续或显式父任务续跑使用，不制造 stopped 完成事件。显式续跑产生的新成功结果沿用原 `applyFinish`，写沟通报告、提交完成事件并更新群聊，进入验收或报告队列。交接提交成功后先清理完成时捕获且身份仍匹配的旧 Tab，再按会话串行后台压缩；跳过或压缩失败不影响关页，验收不等待这段收尾。回报或完成事件提交失败时保留 Tab，不放行压缩。这与上文仅凭已持久化回执恢复调度、而不重放副作用的路径不同。

恢复控制器纳入 `collectRunningLoopTaskIds`，即使主任务没有直接 CLI 进程，仍可等待子任务、接收完成事件与停止。群聊按钮不能只依据主 Tab 忙闲判断：父任务仍为 `running` 且 scheduler 存在任何非中断的开放 attempt 时，隐藏普通“继续执行”并保留“中止”；仅当没有活动 attempt 且仍有 `blocked` 子任务可恢复时，才允许显式续跑恢复。面板投影与宿主消息处理共用该门禁，避免状态刷新间隙或过期消息绕过，保证“中止”和“继续执行”互斥；真实主模型调用忙时仍不重复启动。切模型是独立的显式主模型路由操作，不受普通续跑门禁误拦；继续文本仍进入 `userMessageQueue` 并由现有调度器消费，切模型在调度前更新主模型提示与持久化路由，保留仍运行的兄弟 attempt。重复通知因原 attempt 已不在 running 而忽略。验收门槛、失败修复和父任务最终完成通知保持原契约。
