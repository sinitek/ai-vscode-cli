# Loop / Loop+ 宿主中断后的完成回报

## 恢复边界

VS Code 或扩展宿主意外退出后，原控制器、等待 Promise 和 CLI 进程句柄均不可继续使用。任务记录、会话消息、子任务沟通文件以及 Loop+ 调度快照是恢复依据；不接管崩溃前的外部进程，也不根据文件内容猜测成功。

`isLoopTaskRunOrphaned` 以当前宿主的真实所有权判断失联，持久化的 `activeSubtaskIds` 不再证明进程存活。运行核对将失去所有权的 running 主任务记为 stopped，并持久化 `runtimeInterrupted=true`；保留活动 ID、Loop+ 原快照和待验收队列，把 running 子任务标为 blocked。用户主动停止清除该标记，并继续走原停止策略。

重新打开不会自动执行任务。用户可在原子任务 Tab 手动继续；完成结果必须来自本次成功运行记录。原记录没有该标记且已经 stopped 时，无法可靠区分历史用户停止与旧版本的状态核对，不猜测恢复原因；应显式继续父任务。

Loop+ 群聊继续按钮区分控制器所有权与主模型调用：控制器可以仍在等待子任务或调度事件，而主模型已经空闲。此时按钮将继续文本放入 Loop+ 用户消息队列，复用对话输入的唤醒路径；切模型先更新运行时提示与模型路由，再排入继续消息，避免用缓存模型抢跑。若没有当前控制器，则显式重建原调度快照。真实主模型调用忙时不重复启动；继续仍保护失败上限、完成状态和无效快照。切模型只有在确实重新启动中断子任务时才由子任务恢复回调接管，否则唤醒主模型。经典 Loop 仍按宿主所有权保护。此入口是用户主动续跑，不会在重新打开时自动执行任务。

## 宿主仍存活时的等待巡检

扩展激活时注册一个 `loopWaitWatchdog.ts` 的 5 分钟周期时钟，分别调用两种 host 的 `checkWaitingTasks`；检查隔离异常，扩展释放时清理时钟。仅处理当前宿主已持有的等待控制器，不扫描磁盘并自动复活冷任务。

真实执行状态来自 Tab 的宿主运行所有权，不能仅依赖 `activeSubtaskIds`、未结束的 Promise 或 scheduler running 预留。准备启动、来源/会话锁、后台压缩、重试和收尾仍算活动。刚开始调用的 5 分钟内保留启动交接宽限，避免在 runner 建立所有权之前误判；已有活动兄弟或手动续跑也阻止恢复。

经典 Loop 保留本批等待上下文，正常成功仍立即推进；中断或失败则保持等待至巡检。若已无活动子任务，放弃失联 Promise、解除本批活动 ID，把尚未完成的子任务保留为 blocked，唤醒现有主编排进入下一轮检查。手动续跑或切模型后全部完成时立即交回原等待控制器，不另启主任务，也不等待下一次巡检。旧调用接收取消信号，来源/会话锁及时释放，迟到 resolve/reject 被消费，不能再写轮次、完成报告或重试；恢复后的提示只把确实完成的子任务列为已完成。

Loop+ 在主模型空闲时核对预留与实际调用。确认无活动子任务后，将失联 attempt 以失败结果写入原沟通文件并排入验收；同次巡检先收集全部失联事件，再唤醒一次主任务。队列中的待启动任务继续按原准入规则推进；已有验收事件优先处理，空队列则进入收尾检查。失败修复、验收批次、协议重试和最终完成门禁均保留，未观测到完成不等于成功。取消失联适配器等待会释放完成订阅、执行根和会话锁；迟到结果不能重复完成或覆盖验收事件。

主任务 stopped、needs-review、error、completed、等待澄清或达到主模型失败上限时不自动唤醒；用户停止和异常恢复仍有不同语义。本机制不是子任务执行超时，不限制仍持有真实执行所有权的长任务。

## 经典 Loop

手动续跑成功复用 `finalizeLoopSubtaskRun`：更新子任务状态与摘要、写沟通记录、通知群聊，再按原条件后台压缩子会话，压缩结束后关闭完成时捕获的子任务 Tab。主任务恢复不等待这段后台收尾；压缩失败仍关页，汇报失败则保留 Tab。活动兄弟任务未完成时保留等待状态；全部活动任务完成后，允许恢复带宿主中断标记的父任务，再继续主任务协调。

最后一个子任务清空活动 ID 与主任务启动之间，关闭标签可能触发面板运行核对。该核对同样保留宿主中断标记，因此不会让随后唤醒失去资格。按父任务 ID 保留唤醒中的内存互斥，避免并发完成回调重复启动主任务。用户主动停止、完成或主模型失败限制仍阻止自动唤醒。

## Loop+

`notifySubtaskContinuation` 在缺少内存控制器时可接收原主任务目标及输入，从任务记录重建调度器。只允许原任务仍 running 或带宿主中断标记的 stopped；拒绝已完成、主动停止、主模型失败限制、非法快照、parentStopped 或不存在的开放 attempt。

恢复时先注册控制器，再发布 running 状态，避免状态刷新在交接间隙再次判为失联。原开放 attempt ID 不变，其余失去句柄的 running 预留保留为 blocked，供手动继续或显式父任务续跑使用，不制造 stopped 完成事件。收到结果的 attempt 沿用原 `applyFinish`，写沟通报告、更新群聊与快照、排入验收并唤醒主任务。完成通知成功处理后放行可选子会话压缩，压缩结束后按完成时的标签快照自动关页；验收继续推进，不等待压缩或关页。结果不能回报时保留该 Tab。

恢复控制器纳入 `collectRunningLoopTaskIds`，即使主任务没有直接 CLI 进程，仍可等待子任务、接收完成事件与停止。该所有权不代表主模型正在执行，不能单独隐藏继续按钮或阻止空闲主模型续跑。继续文本进入 `userMessageQueue` 并由现有调度器消费；切模型在调度前更新主模型提示与持久化路由，保留仍运行的兄弟 attempt。重复通知因原 attempt 已不在 running 而忽略。验收门槛、失败修复和父任务最终完成通知保持原契约。

## 验证

- `src/test/extensionHost/loopWaitWatchdog.test.ts`：5 分钟周期、释放与异常隔离、经典准备/执行/失联/中断及拒绝恢复边界。
- `src/test/extensionHost/loopPlusOrchestration.test.ts`：活动调用保护、失联批量验收去重、手动续跑保护、迟到回调和停止/暂停门禁。
- `src/test/extensionHost/loopCrashRecovery.test.ts`：真实临时磁盘任务存储、host 重建、兄弟任务等待、标签刷新交接、并发通知、主动停止及非法快照；另起 Node 子进程写状态后强制终止，再重建宿主并回报。
- `src/test/extensionHost/loopPlusRuntimeIntegration.test.ts`：用真实适配器与磁盘任务记录，从冷通知到主模型验收、沟通报告、父任务完成和控制器释放；模型回复使用脚本夹具；另启动本机 Node 子进程以状态 9 退出并保留未完成 Promise，验证巡检后失败验收、沟通报告、订阅及会话锁释放。5 分钟边界以受控时钟推进，不等待实际 5 分钟。
- 验证命令：`npm run build` 后运行上述编译后的测试及相关 Loop/Loop+ 回归。进程强制终止测试不等同于 VS Code 图形宿主或真实模型验证。
