# Loop+ 启动前配置锁超时后显式继续

- 日期：2026-11-18
- 类型：bugfix
- 状态：completed
- 负责人：Codex（本次执行）；主任务负责验收

## 背景与目标

原任务主模型启动前五次等待共享配置锁超时。暂停摘要指向群聊「继续执行」，但失败上限同时拦截投影和宿主；普通聊天不能恢复该任务。恢复原群聊的显式入口，保留同一任务和验收队列。

## 范围与验收

- 投影和绑定群聊的显式操作复用启动前锁超时资格检查；新记录识别结构化错误码，旧记录按完整固定消息兼容。
- 第二轮补生产启动交接：在任务和队列写入前取得严格匹配原档案修订的既有执行租约，再重读取同一物理来源并复核原任务、工作区、CLI、会话、标签与快照。首轮调用消费同一租约，沿调用生命周期释放；拒绝、取消及未消费有有界清理。
- 恢复或准入期间若超时、目标漂移或繁忙，保留暂停、计数、冻结验收和待派发，不启动新重试。成功交回既有原任务续跑路径。
- 保留路由、去重、依赖准入、部门与 Owner 边界，不更改 UI 或操作真实任务、配置锁和运行中扩展。

## 验证与交接

- 物理副本使用独立 `HOME`、`TMPDIR` 和 `dist/`；运行 `npm run build`、受影响定向测试和 `python3 .agents/skills/ontology/scripts/search_ontology.py --validate`。
- 第一轮的群聊资格、失败来源、存储与配置等既有定向证据仍按覆盖范围复用。第二轮在恢复成功与执行准入之间注入锁超时、档案或同档案修订变化，及取租约后目标变化；增加最小隔离 VS Code 宿主公开群聊入口检查，只使用合成任务和本地 CLI 替身。不重放产研部已有检查或真实任务。
- 第三轮把落盘与派发移到实际会话的非抢占准入边界：持租约完成交互准备后再冷读原记录，拒绝既不写入也不重试，保留调用原错误。对齐 `origin/master` 自 `07953676` 的 v1 依赖读取、校验、复制和执行准入，沿用本分支冻结验收顺序和现有验收协议，不迁移真实记录。隔离验证与覆盖边界见第三轮独立报告。
