## 背景与范围

新建 Tab 的首次发送仍需取得目标 CLI 的全局配置锁。本机出现过 Codex 启动等待超时；隔离实验确认 `1.9.11` 解锁失败可在持锁进程仍存活时留下残锁，现场是否由同一失败导致未确认。本轮修复共享锁清理、恢复和诊断，不变更配置档案、模型、会话等业务数据，不卸载、重新加载或发布用户正在使用的扩展。

## 验收与风险

- 临时解锁失败自动重试；本进程不能移除锁时，其他窗口只凭明确的事务结束证据安全回收。正常解锁与回收不能竞态删除随后取得的锁。
- 真正仍在运行的持锁事务、不同档案、未就绪配置不得放行；旧版锁按原规则识别；不同项目的同档案任务保持可并行。文件系统持续不可写时保守失败。
- 日志区分争锁、超时、解锁异常和回收，能关联进程、操作和时长，不记录配置、凭据或原始路径。回滚前先关闭所有窗口，旧版本仍能读取原有锁结构和选择记录。

## 验证计划

- 先补独立 Node 进程的故障注入回归，确认原版复现，再实施修复。
- 执行 `npm run build`、配置锁/启动/租约/Loop+ 定向测试，再运行更广的单测；用临时文件系统测试真进程竞争、首发恢复和不误拆活锁。
- 同步运行时参考、排障手册、功能清单和 ontology，记录未覆盖环境。

- 以匿名 `lockId` 串联慢事务、释放重试或延期、回收、超时；关联 PID、操作、等待/持有时间和系统错误码，不记录路径、token 或配置文本。排障边界已同步到 runbook、运行时参考、功能清单和 ontology，不重复写热区记忆。
