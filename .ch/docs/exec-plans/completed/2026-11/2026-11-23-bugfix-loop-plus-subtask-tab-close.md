## 背景

用户持续看到 Loop+ 子任务显示“子任务执行结束，用时 15:30，等待主任务验收。”但对应标签仍打开；此前已有 2026-11-14、2026-11-15 的收尾修复。只读核对本机 `~/.sinitek_cli/logs/`、`tasks.json` 与历史计划，日志无法把用户所指实例唯一关联到关闭结果：成功事件使用受调试开关过滤的 `logInfo`，当前保留日志没有近期成功/失败关页事件；本机运行记录来自多个工作区，不能据时长臆定实例。代码复现确认另一漏关路径：Loop+ adapter 将关闭 Promise 缓存到 attempt 生命周期结束，关闭异常被普通任务的 best-effort 回调吞掉，后续没有自动重试；现有测试夹具还在抛异常前就记为“已关闭”，掩盖了该失败。终态提示来自 CLI run 收尾，先于 Loop+ 回报提交与标签清理，不代表后两者成功。

## 目标

沿 Loop+ 子任务的完成提示、主任务回报提交和 VS Code 标签关闭链路，确认仍可复现的静默漏关根因；修复根因并用回归测试覆盖关闭成功、回报未提交及身份不匹配的边界。让后续日志能区分“尚未提交回报”“安全守卫拒绝关闭”“关闭失败”和“关闭成功”。

## 当前结论

已确认并修复可复现的静默漏关路径：完成回报提交后若宿主关页抛出瞬时错误，adapter 会复用已拒绝的 Promise，且 best-effort 回调不重试；旧测试夹具误将失败调用计为关闭成功。当前自动派发与手动续接共用一次有界重试；失败缓存清除以允许后续再次调用；日志默认记录报告失败、关闭失败及关闭成功。用户所见实例没有足够日志/运行身份可关联，不能断言它具体命中了哪一分支。最终验证通过：构建、定向回归、69 项 Loop+ 集成、本体校验及差异检查；计划可以归档。
