# Loop 熔断前的恢复方案澄清

- 日期：2026-11-23
- 类型：feature
- 状态：completed
- 负责人：Codex

## 背景与目标

Loop、Loop+ 和产研部已能报告阻塞原因，但仍可能在有可执行恢复方案时暂停。先推进安全独立工作；必要时弹出可执行方案，按现有人机交互超时自动采用推荐方案并续跑。

## 范围与边界

- 复用结构化阻塞诊断、持久澄清、群聊弹窗、交互历史和现有超时设置。
- 环境、资料、依赖、实施路径等都能提出方案；超时不视为新授权，宿主不执行任意修复命令。
- 不改真实 CLI 调用失败、权限、停止、组织信任、验收及完成门禁。

## 验收与验证

- 验证手动选择、超时推荐、重复方案不再弹出，以及无有效方案时保持原暂停行为。
- 验证经典 Loop、Loop+ 和部门路由，运行 `npm run build`、相关 `node --test` 和 ontology 校验。
- 同步功能清单及 Loop+、产研部设计。

## 验证结果

- `npm run build` 通过；`node --test` 共执行 11 个相关测试文件、636 项全通过，日志位于 `.tmp/loop-blocker-recovery-tests.log`。
- 模拟 CLI 返回可恢复诊断，确认经典 Loop 和产研部总监进入既有待澄清状态；Loop+ 用原澄清等待器验证手动提交备选、非法值拒绝、配置超时选推荐、清理待交互及继续决策。验证无新可行方案仍可暂停，保留原完成门禁。
- 回归中发现普通调度不应新增异步让步，修复后容量时序通过；普通澄清超时文案保持兼容，仅恢复方案明确说明宿主默认选择及未增授权。
- `python3 .agents/skills/ontology/scripts/search_ontology.py --validate` 和 `git diff --check` 通过。此次验证为宿主模拟，未运行真实模型、安装软件或执行实际环境修复，未改 Webview UI。
- 稳定规则已同步功能清单、设计、ontology；不需要重复写入滚动摘要。
