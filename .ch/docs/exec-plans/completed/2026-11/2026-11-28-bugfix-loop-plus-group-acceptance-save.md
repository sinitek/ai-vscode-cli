# Loop+ 群聊验收方案保存与回显

- 日期：2026-11-28
- 类型：bugfix
- 关联计划：无
- 状态：completed
- 负责人：Codex

## 背景与范围

群聊「保存」写入工作区模板。重开弹窗读取当前任务快照，因此会显示保存前的勾选。群聊的增量刷新也缺少这份快照。修复范围是普通 Loop+ 群聊、对应宿主消息和回归验证，沿用现有任务存储和验收运行时。

## 验收与验证

- 在群聊保存自定义模板时，将宿主确认的模板同时应用到当前任务。单独保存到任务时支持默认方案及清空附加项。
- 重开弹窗、增量刷新以及重建面板都显示任务持久化的勾选和「其它」文本。刷新期间保留正在编辑的草稿。
- 写入失败时提供可重试的反馈，保留上次生效的任务方案，区分模板已保存但任务应用失败。
- 更新进行中复核或收尾的方案时，重新请求当前轮验收，保持父任务与子任务执行。用户同时中止时，以用户操作为准。
- 从宿主路由和 Webview 最小回归开始，运行 `npm run build`、相关 `node --test`，在 Chromium 中验证实际点击与重开。

## 修复结果

群聊以当前任务的持久化快照回显勾选。两种保存操作都使用宿主确认的结果。任务写入失败可以在弹窗中重试。模板已写入时，重试复用同一模板 ID。弹窗关闭后焦点回到群聊的验收方案按钮。

运行适配器回报旧验收调用已取消时，调度器先检查父任务是否已经停止，再判断该轮是否被新方案替代。替代轮次复用原冻结批次，收尾保留执行机会。意外中断的验收在自动续跑时重新核对原会话和发送资格，并使用最新方案。

## 验证记录

- 修复前，群聊保存用例重开仍显示 `security`，任务应用调用次数为 0。真实运行适配器的复核测试读到父任务 `stopped`。修复后，复核与收尾都使用新快照，同一个父任务完成，子任务只执行一次。并发主动停止会保留 `stopped`，旧回复不能重启任务。
- 自动续跑的三个用例覆盖等待恢复、发送前及发送后修改方案，均核对同一复核事件、原会话和发送资格。
- `npm run build` 通过。14 个相关测试文件共 681 项通过，失败、取消、跳过均为 0。记录见 `.tmp/loop-plus-group-plan-regression-final.log`。Ontology 结构校验与 9 项工具测试通过。
- Chromium 通过 5 个场景，覆盖编辑时刷新、模板与任务保存后重开及整页重载、仅清空任务附加项、任务写入失败重试和模板部分写入后重试。使用生成的 Webview、群聊宿主路由、模板与任务更新入口以及临时任务文件，页面和网络错误均为 0。记录见 `.tmp/loop-plus-group-plan-browser-S3WEj0/result.json`。
