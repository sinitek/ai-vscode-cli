# Loop+ 子任务回报遇到身份锁时保留交付

- 状态：completed
- 负责人：Codex
- 关联计划：`.ch/docs/exec-plans/completed/2026-11/2026-11-28-bugfix-loop-plus-completion-commit.md` 覆盖主模型完成提交，本次处理子任务回报。

## 证据与目标

安装版宿主在子任务回报提交之前多次记录读取被身份事务锁拒绝，随后在 `finish-commit` 记录 `update-unconfirmed`，中断正在进行的验收。普通 Loop+ 应保留已经返回的执行结果，取得权威记录后继续提交。身份不符、任务被停止或提交失败须有明确处置。

## 范围与风险

检查父任务的权威读取、完成凭据、调度事件提交、报告和清理通知的先后顺序。重试必须验证原 attempt，并保持并行回报、已冻结验收、用户停止、部门所有权与真实存储错误的语义。历史实例只读。

## 任务与验证

- [x] 使用隔离 HOME 和真实事务锁复现子任务回报中断。
- [x] 修复提交路径，记录竞争阶段和恢复结果，验证副作用次数。
- [x] 运行构建、相关测试与本机验证，同步功能清单、设计和本体。

## 根因与修复

子任务完成时，旧宿主先改变内存调度状态，再读父任务和写回报。身份事务锁暂时挡住读取时，空记录被当作提交失败，宿主取消了正在验收的主回合。现在普通 Loop+ 按开放的 attempt 保存原结果，在副本上准备事件，用父记录的版本提交。明确的提交前竞争先退避，仍遇锁时交给同一宿主的分钟巡检。成功写入后才放行群聊通知、成功清理和后续派发。阶段、重试次数和结果可通过 `loop-plus-finish-contention` 的事件键关联。恢复边界见[调度设计](../../../design-docs/loop-plus-scheduling.md#子任务回报遇到存储竞争)。
