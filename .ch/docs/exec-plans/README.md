# 执行计划目录说明

这个目录仅承载 `feature`、`bugfix`、`refactor`、`perf` 类型的非平凡任务计划与收尾记录。

本页是执行计划规则的单一事实源；文档总入口统一收口到 `.ch/docs/README.md`。

## 结构

- `active/`：正在推进的任务
- `completed/YYYY-MM/`：已经完成并按月份归档的任务
- `TEMPLATE.md`：计划模板
- `tech-debt-tracker.md`：不单独建计划的小型后续项

starter 默认不保留历史计划文件；复制模板后再从真实任务开始积累。

## 命名与分类

`test`、`chore`、`doc`（含 `docs`）类型任务不在本目录创建或归档计划，也不得改名为允许类型来绕过排除规则。独立的测试、维护或文档任务使用任务列表、测试记录或对应事实来源文档；相关工作属于某份允许类型计划的交付范围时，在该计划中记录范围、验收与验证结果，不另建计划。排除计划文件不免除测试、验证和文档同步要求。

本次规则同步不自动改名、迁移或删除既有计划，也不改写历史状态与证据；既有计划、迁移审计、记忆热区和 generated 索引采用保留式合并。

真实计划文件名必须严格为 `YYYY-MM-DD-<type>-<kebab-case-slug>.md`：日期后紧接且只出现一个 type。允许值仅为 `feature`、`bugfix`、`refactor`、`perf`；不要使用 `feat` 或 `fix`。

| Type | 适用范围 |
| --- | --- |
| `feature` | 新功能开发 |
| `bugfix` | 修复已发布版本中的 bug |
| `refactor` | 不改变外部行为的重构 |
| `perf` | 性能优化 |

示例：`2026-03-28-feature-workspace-search.md`。完成后的归档路径为 `completed/2026-03/2026-03-28-feature-workspace-search.md`。

一个任务包含多个允许的实质工作类型时，必须仅按允许类型分别建立计划文件。每份计划都要有自己的目标、范围、验收标准、验证计划和真实状态；“关联计划”必须写出具体相对路径，并说明共同背景和依赖。禁止只选一个主类型、在一个文件混合多个允许 type，或复制整篇混合正文来冒充拆分。实际跨类型工作不得藏在附带事项中。`test`、`chore`、`doc`（含 `docs`）不参与计划拆分。

跨类型示例：新功能与独立性能优化分别记录为 `active/2026-11-11-feature-workspace-search.md` 与 `active/2026-11-11-perf-workspace-search-index.md`，并在双方“关联计划”中互链、写明依赖。两份记录各自维护目标、范围、验收、验证和状态，不复制混合正文；新功能所需的回归测试开发和文档同步直接记入功能计划，不创建 `test` 或 `doc` / `docs` 计划。若其中一份受阻，另一份保留真实状态，不因关联关系伪造完成。

归档月份取计划文件名或计划日期中的 `YYYY-MM`，并按 `YYYY-MM` 创建月份目录。完成计划不得平铺在 `completed/` 根目录；需要枚举历史计划时必须递归扫描 `completed/**/*.md`，并使用完整相对路径作为计划标识。

目录示例：

```text
completed/
├── 2025-06/
│   └── 2025-06-18-feature-workspace-search.md
└── 2026-03/
    └── 2026-03-28-refactor-workspace-search-index.md
```

## 使用原则

- 计划是执行载体，不是汇报材料。
- 计划必须可延续：下一位代理或下一次会话看到它就能继续推进。
- 计划头部状态明确标记为 `completed` 后，要归档到对应的 `completed/YYYY-MM/`，不要长期堆在 `active/`。
- 按允许类型拆分计划时分别追踪真实状态；不得伪造完成状态，也不得改变既有阻塞状态。
- 移动计划后必须同步更新仓库内引用该计划的具体路径，并验证引用目标存在。
- 迁移审计资料（如有）从 `migrations/` 查阅；审计映射不替代真实计划或完成状态。
- 计划内容不要停留在本目录：稳定架构进入 `ARCHITECTURE.md`，规则进入 `AGENTS.md` 或 `.ch/docs/*.md`，复发问题进入 `runbooks/`，用户可见能力进入 `product-specs/FEATURE_INVENTORY.md`，跨会话优先上下文进入 `memory/`。

## 什么时候建计划

仅适用于 `feature`、`bugfix`、`refactor`、`perf` 类型，且满足以下条件之一；独立的 `test`、`chore`、`doc`（含 `docs`）任务不因复杂度、风险或跨会话要求而建计划：

- 一个任务超过一个阶段。
- 涉及多个目录或多个角色。
- 涉及风险、迁移、治理、跨系统依赖。
- 需要为下一次会话留下清晰上下文。

## 每份计划至少包含

- 背景与目标
- 范围与非目标
- 验收标准
- 影响面
- 风险与回滚/缓解思路
- 验证计划
- 单元测试变化、单元自测命令、失败处理结论或未补原因
- 功能清单是否需要同步
- 当前进展与下一步

## 收尾前必查

- 是否补了本次应有的单元测试；如果没有，是否明确记录原因与后续动作。
- 有一定复杂度的功能是否已经自动执行单元自测；若失败，是否按 `.ch/docs/TESTING.md` 完成合理修复、隔离或记录。
- 如果功能、行为、权限、流程发生变化，是否同步 `.ch/docs/product-specs/FEATURE_INVENTORY.md`。
- 是否写明验证了什么、没验证什么、为什么。

## 轻量 claim / release

多会话或多代理并发时，可在计划头部元信息区增加：

- `owner`：当前主要负责推进的人或代理
- `claimed_at`：开始占用该计划的时间
- `claim_ttl`：占用预计保持多久，或何时应该重新确认
- `handoff_to`：准备交接给谁，或下一次默认接手对象
